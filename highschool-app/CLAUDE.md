# 고등부 통합 웹페이지 운영 지침

루트 `../CLAUDE.md`가 최우선 규칙입니다. 이 문서는 통합 앱에만 해당하는 보충 지침입니다.

## 목적

### 학생 이동 후 과거 신청과 현재 원장 연결 (2026-09-12)
- **접근법**: `applicationForRosterPerson`으로 기존 신청을 찾는다 → 접수 저장·삭제·비공개 정보는 기존 신청 키를 유지한다 → `rosterContact`와 찬양 `officialRosterReader`에서 personId로 현재 학생을 확인한다.
- **판단 질문**: 과거 신청 키를 교체하면 학기 출석·비공개 자료·찬양 연결이 끊긴다. 학생 앱에서 다른 앱 경로를 역방향 수정하지 않는다. 찬양 정상 후보는 단건 조회를 유지하고 이동 후보가 있을 때만 연도 명단의 유일한 영구 ID를 확인한다. 이름만 같은 학생은 연결하지 않는다.
- **재사용 규칙**: `rosterIdentity.test.ts`, `movedRoster.test.ts`, `rosterRead.test.ts`의 이동·동명이인·키 충돌 계약을 유지하고 새친구 삭제의 결정적 ID 보호를 완화하지 않는다.

학기 운영, 팀·주일 운영, 수련회 행정, 이가드 현장 기능을 `highschool-app` 한 코드베이스와 배포 단위로 운영합니다. 독립 `retreat-app`·`iguard-app`은 2026-08-05 제거했지만 운영 DB 경로와 데이터 형태는 그대로 유지합니다.

## 라우트

- `/`: 통합 홈
- `/ministry-guide`: 위키에서 추린 월별 사역 흐름·부서 운영 가이드 라인(권한 있는 담당자 편집 가능)
- `/teams`, `/teams/[team]`: 팀 중심 운영의 기본 진입점. 각 팀 안에서 상시 업무와 연결된 학기(`terms/[semesterId]`)를 함께 관리합니다.
- `/training`, `/training/terms/[semesterId]/[section]`: 기존 `semesters/*` 학기 원장을 그대로 읽는 훈련 중심 진입점. 훈련반·명단·훈련 출석·커리큘럼을 모으며 별도 DB를 만들지 않습니다. 연락처는 Rules와 같은 중앙 역할만 `semestersPrivate/*`에서 신청 ID로 결합합니다.
- `/operations`, `/operations/semesters/[semesterId]`: 통합관리자·교역자·행정팀의 학기 개설·신청·배치·공용 자료·계정·로그 운영센터입니다. `/semesters`, `/semester/[id]`는 기존 주소 호환용으로 유지합니다.
- `/sunday-ministry`, `/sunday-ministry/[team]`: 기존 주일 업무 주소. 팀은 `행정팀`(`admin`)·`바나바팀`(`barnabas`)·`예배팀`(`worship`)·`찬양팀`(`praise`)·`미디어팀`(`media`)·`기획디자인팀`(`design`) 여섯이며 팀 중심 주소와 같은 원장을 사용합니다.
- `/retreats`, `/retreat/[id]`: 수련회 행정
- `/programs`, `/retreat/[id]/programs`: 수련회 프로그램 준비. 수련회당 기본 2개 초안을 선택 생성하고 필요하면 3개 이상으로 늘립니다.
- `/retreat/[id]/field`: 이가드 현장 운영

서비스 이름은 **분당우리교회 서현고등부**이고, 운영 주소는 `https://woorihigh-app.vercel.app` 입니다(구 `highschool-app-flame.vercel.app`도 같은 배포를 가리킵니다).

## 화면 셸 규칙

- 사이트 제목·계정·로그아웃·상단 메뉴는 `GlobalPortalHeader` 하나만 담당합니다. 하위 화면에 "수련회 행정시스템" 같은 제목 줄을 다시 만들지 않습니다(제목 2줄 중복 금지).
- PC 헤더의 계정 제어 순서는 **`PC버전/모바일버전` → `라이트/다크 모드` → `마이페이지`**입니다. 저장된 선택이 없는 첫 접속만 실제 900px 이하 뷰포트를 모바일 기본값으로 사용하며, 사용자가 고른 화면 모드는 이후 창 너비보다 우선합니다. `PC버전`은 처음부터 같은 출처의 최소 1280px iframe 하나에서 실행해 창을 줄이거나 늘려도 React 트리와 문서를 교체하지 않으며, 좁은 창은 가로 스크롤로 PC 화면을 유지합니다. `모바일버전`은 PC용 미리보기 제어 막대 아래 같은 출처의 430px iframe으로 실행합니다. 내부 프레임 표식 `__portalFrame=desktop`은 바깥 주소에 노출하지 않고, iframe의 경로만 바깥 URL과 동기화합니다. 데스크톱 DOM을 CSS로 억지 축소하거나 반응형 분기를 수동 덮어쓰지 않습니다.
- 모바일 학기 화면은 `출석 / 신청·배치 / 커리큘럼 / 운영`, 팀·주일 화면은 팀 선택 후 해당 팀 탭, 방학 현장은 `큐카드 / 포스트 / 인원체크 / 정보`를 1차 업무축으로 씁니다. 유효한 `?tab=`이 있으면 화면 폭보다 먼저 적용하고, 쿼리가 없는 모바일 학기 진입에만 출석을 기본으로 둡니다. PC의 기존 상세 탭과 URL은 제거하지 않습니다.
- 상단 메뉴는 **학기 운영 / 팀·주일 운영 / 방학 중 사역 / 사역 가이드 / 사이트 건의사항** 순서입니다. 팀·주일 운영과 방학 중 사역은 **둘 다 hover 드롭다운**이며 공용 `NavDropdown`(`GlobalPortalHeader.tsx` 내부) 하나를 씁니다 — 마크업·키보드·바깥클릭 동작이 갈라지지 않게 여기에만 두고, 열림 상태는 부모의 `openMenu`가 들어 한쪽을 열면 다른 쪽이 닫힙니다. 팀·주일 운영은 `행정팀`·`바나바팀`·`예배팀`·`찬양팀`·`미디어팀`·`기획디자인팀`, 방학 중 사역은 `수련회 행정팀`(`/retreats`)·`수련회 프로그램팀`(`/programs`)·`수련회 이가드팀`(`/field`)으로 갈라집니다.
- **팀·주일 운영의 팀·탭 배치는 `featureCatalog.ts`의 `SUNDAY_MINISTRY_TEAMS`가 단일 원천**입니다. 화면이나 헤더에서 팀 목록을 다시 적지 않습니다. 팀별 `tabs`의 합집합은 반드시 `SUNDAY_MINISTRY_TABS`와 같아야 하며(중복 배치도 금지) `featureCatalog.test.ts`가 이 계약을 지킵니다 — 팀을 늘리거나 탭을 옮길 때 탭이 조용히 사라지는 것을 막습니다. 찬양팀은 `PRAISE_TABS`의 다섯 탭을 사용합니다. 미디어·기획디자인팀은 기능 확정 전까지 `tabs`가 비어 있고, 탭 바 없이 준비 중 화면만 렌더합니다.
- **팀 권한은 `teamMemberships/{teamKey}`의 `role`·`active`·선택적 `semesters`가 원천**입니다. 두 계정 버킷에 나뉜 연결은 병합해 읽고, `viewer`는 조회만 하며, 학기 범위가 있으면 그 학기의 목표·커리큘럼·출석만 수정합니다. 스탭팀장은 모든 팀의 공개 운영 기록을 조회하지만 현재 Rules에 맞춰 연결된 팀만 수정합니다. 팀 학기 명단의 연락처는 팀 조회 범위 안에서 `classes/*`·`teacherStaff/*` 공식 원장값만 보여주며, 일반 팀원에게 `semestersPrivate/*` 신청서 값을 열지 않습니다. 공용 자료 수정은 운영센터에서만 허용합니다. UI와 Firebase Rules 중 한쪽만 넓히지 마세요.
- **예배팀 자리 배치**(`features/sundayWorship`)는 Rules를 바꾸지 않으려고 **사역 가이드와 같은 공유 노드**(`prepMilestones`)에 `sourceSite=sunday-worship-seating` 조각으로 저장합니다. `note`가 500자 제한이라 **분단 하나 = 레코드 하나**로 쪼개고, id는 `ws_{YYYYMMDD}_{부}_{분단}`으로 결정적입니다. 분단을 줄이면 남은 레코드를 같은 update에서 `null`로 지워 화면에 없는 분단이 DB에만 남지 않게 합니다. **일정 구독 두 곳**(`lib/db/shared.ts`·`features/iguard/lib/db.ts`)이 `isWorshipMilestone`으로 이 조각을 걸러냅니다 — 새 조각을 추가하면 두 곳 모두 갱신하세요.
- 화면은 **줄 × 분단 표**입니다. 왼쪽에 줄 번호를 세우고 분단을 열로 놓아 실제 좌석표와 같은 모양으로 읽습니다. **줄 높이는 `gridTemplateRows`로 고정값(`3.75rem`)을 줍니다** — `auto`로 두면 내용이 있는 줄만 커져 분단끼리 줄이 어긋나고, 좌석표에서 줄 정렬은 장식이 아니라 기능입니다. 칸 안 숫자는 `.input`을 쓰지 않고 직접 그려(`CELL_NUMBER`) 글자처럼 납작하게 둡니다.
- 칸 안 숫자는 **`2줄`처럼 단위를 붙여** 보여줍니다. `type="number"`는 웹킷 스피너가 좁은 폭을 다 먹어 숫자가 사라지므로 **`type="text" + inputMode="numeric"`**을 쓰고 입력값에서 숫자만 걸러 받습니다. 입력칸 폭을 글자 수에 맞춰야 단위와 붙어 보이는데, 그러면 클릭 영역이 좁아지므로 `label`로 감싸 "줄" 글자를 눌러도 포커스가 잡히게 합니다.
- 칸 색은 **고정석(에메랄드) / 자동 계산값과 다른 칸(앰버) / 그대로(기본)** 세 가지이고, "고친 칸"은 저장하지 않고 `block.rows !== rowsForAverage(...)`로 파생합니다. 하단 범례가 이 세 가지를 설명합니다.
- 격자는 **분단 × 분단별 줄**이고 **한 반이 여러 줄을 차지**합니다. 배치도의 `1-5(2)`는 인원이 아니라 그 반이 쓰는 **줄 수**입니다. 인접은 같은 분단의 위아래(앞뒤)와 인접 분단의 같은 줄(좌우)이며, 블록이 **위에서 두 줄과 겹치면 앞자리**입니다(`isFrontBlock`).
- **줄 수 = 올림((지난 3주 출석 평균 + 담임 1명) / 한 줄 의자 6개)** 입니다(`rowsForAverage`). 전체 명단으로 계산하면 허수가 많아 출석 평균을 씁니다. 출석은 `O`를 세며 이전 저장값 `T`도 `O`로 호환 처리합니다. 셀 키는 학생 출석부의 `evKey`와 같은 `{월 인덱스}-{그 달 몇 번째 주일}` 규칙입니다(`sundayCellKey`) — 이 규칙이 어긋나면 출석을 못 읽습니다. 해가 바뀌는 주는 다른 연도 노드라 계산에서 뺍니다.
- 화면의 반 라벨은 `학년-반`이고 **예배 부는 classKey(`part-grade-class`)의 앞자리**로 매칭합니다(`classKeysForService`).
- ⚠ **이 앱의 타입 스케일은 좁습니다** — `text-xs`=12px, `text-sm`=13px, `text-base`=14px, `text-lg`=17px. Tailwind 기본값(12/14/16/18)과 달라서 한 단계 올려도 1px밖에 안 커지는 구간이 있습니다. 글씨를 실제로 키우려면 두 단계를 올리거나 실측으로 확인하세요.
- ⚠ 이 화면의 숫자 입력칸은 **폭을 감싼 div로, 글꼴·좌우 여백을 인라인 style로** 줍니다(`NUMBER_INPUT`). `.input`이 `@layer` 밖이라 `w-*`·`text-xs`를 모두 이기고, 기본 좌우 패딩 14px씩이면 콘텐츠 폭이 14px만 남아 숫자가 잘립니다(실제로 반 이름 폭이 0이 된 적 있음). **`min-h-*`도 마찬가지로 먹히지 않습니다** — 예배 자료의 본문 textarea는 `BODY_TEXTAREA` 인라인 style로 높이를 줍니다(유틸리티만 쓰면 320px가 65px로 찌그러집니다).
- **예배 담당표**(`sourceSite=sunday-worship-duty`)는 역할 한 줄 = 레코드 하나이고, **학생 명단을 구독하지 않습니다** — 이름은 직접 입력합니다. 명단을 끌어오면 이 화면 하나 때문에 개인정보 공개 범위를 새로 정해야 하므로, 편의를 위해 명단 연동을 추가하지 마세요.
- **예배 자료**(`sourceSite=sunday-worship-doc`)는 본문이 500자를 넘으므로 320자 조각으로 나눠 저장하고 읽을 때 합칩니다. **조각이 하나라도 비면 그 문서는 기본값을 씁니다** — 반쪽 문서를 만들지 않기 위한 계약이고 `worshipContent.test.ts`가 지킵니다. 기본 문서는 `DEFAULT_WORSHIP_DOCS`이고 저장된 수정본이 그 위를 덮습니다.
- 팀 라우트를 오갈 때 클라이언트가 재사용될 수 있으므로 **선택 탭은 렌더 중 파생으로 보정**합니다(`tabs.find(...) ?? tabs[0]`). effect에서 setState로 맞추면 실수 13(시계·자동 선택이 사용자 선택을 덮음)과 같은 부류의 회귀가 납니다.
- 우측 계정 메뉴의 **마이페이지**는 모든 로그인 사용자에게 열고 `대시보드`·`내 사역`·`내 요청`을 공통 제공한다. 관리 3탭(`팀원 관리`·`요청사항`·`활동 로그`)도 모든 계정에 표시하되 접근 capability가 없으면 안내만 보여준다. 허용된 관리 탭은 각각 `/operations/accounts`·`/operations/requests`·`/operations/activity`로 연결하며 중복 관리 편집기를 마이페이지에 마운트하지 않는다. 링크는 prefetch를 끄고, 일반 내부 클릭은 같은 경로여도 모달을 닫으며 수정키 클릭은 유지한다. 역할별 대시보드는 `accessPolicy.ts`의 capability로 일정과 바로가기를 필터링하며 역할 문자열을 컴포넌트에서 직접 비교하지 않는다. 학기 신청과 현장 스탭 연결은 현재 계정 이름 후보가 유일할 때만 표시하고 동명이면 미연결 상태를 유지한다. 별도 집계 노드를 만들지 않고 기존 `semesters`·`retreats`·`prepMilestones`·`iguard`·본인 `siteRequests`를 활성 탭에서 실시간 구독한다. 사이트 건의사항은 공유가 아니라 `iguardPending/{uid}/siteRequests/{requestId}`로 전송한다. 이 경로는 기존 Rules의 사용자 자기 읽기·쓰기와 통합관리자 전체 읽기·쓰기를 재사용하며, 접근 승인 필드(`email`·`name`·`requestedAt`)와 반드시 분리해 정규화한다. 승인·거절 시 사용자 노드 전체를 지우지 말고 접근 필드만 지워 요청을 보존한다. 첨부는 JPEG로 재인코딩·축소한 뒤 Firebase Storage의 `site-requests/{uid}/{requestId}/attachment.jpg`에 두고, RTDB 요청에는 이름·크기·Storage 경로·다운로드 주소만 저장한다. 분리 전 `dataUrl` 첨부는 읽기 호환만 유지한다. 요청 삭제 시 Storage 파일을 먼저 지우고 요청 레코드를 지운다. 해결 시 `resolvedAt`을 기록하고 작성자는 다음 로그인 때 한 번 알림을 받은 뒤 `notifiedAt`을 남긴다.
- **방학 중 사역 홈은 화면 하나**입니다. 세 경로 모두 `features/portal/VacationHome.tsx`를 렌더하고, `mode`("admin"/"program"/"field")로 **수련회에 들어갔을 때의 목적지만** 달라집니다(행정 화면 / 프로그램 준비 / 현장 화면). 목록·수련회 기간·준비 일정 캘린더는 완전히 같은 컴포넌트를 씁니다. 각 라우트는 로그인·권한 게이트와 도메인 전용 요소(행정: 폼 가이드·삭제·브레인스토밍 / 프로그램: 프로그램별 편집 / 현장: PIN 배지·현장 관리자)만 슬롯으로 넘깁니다.
- **프로그램 준비의 공개 원본은 `retreats/{id}/programs/{programId}`**입니다. 한 수련회 안에 프로그램을 여러 개 두고, 각 프로그램의 `posts`에는 게임·묵상·영상·브리핑·이동·세팅·예배·정리처럼 서로 다른 `activityType`을 섞습니다. 기존 게임 데이터는 `activityType`이 없어도 그대로 게임으로 읽습니다. `tasks`는 `todo / doing / blocked / done` 실행 상태를 쓰되 구버전 `done` boolean도 계속 읽습니다. 준비회의 원문과 결정은 현장 역할에 노출하지 않고 **`retreatsPrivate/{id}/programMeetings/{programId}/{meetingId}/decisions/{decisionId}`**에 둡니다. private 구독은 편집 권한자에게만 열고 공개 프로그램 캐시에 넣지 않으며, 결정→할 일 전환은 결정적 작업 ID와 최신값 사전 확인 후 public 작업·private 링크를 root multi-location update 한 번으로 반영해 재시도에도 기존 작업을 덮지 않습니다. `competitionTeams`는 프로그램 안에서만 여러 기본 조를 묶는 연합팀이며, **행정 `groups`를 절대 수정하지 않고 groupIds로 참조만** 합니다. 화면 방문만으로 초안·회의·팀을 만들지 않고 사용자가 만들기·추가·적용을 눌렀을 때만 씁니다. **현장의 구독은 `features/iguard/lib/db.ts`의 읽기 전용 영역을 거칩니다** — 훅이 `@/lib/db` 배럴을 직접 쓰면 삭제·수정 함수까지 사정권에 들어옵니다. 편집기는 작성 중 들어온 원격 갱신으로 초안을 덮지 않으며, 상태·종류·활동 라벨은 메타 함수로 읽어 모르는 과거 값에도 화면이 죽지 않게 합니다.
- **수련회 프로그램 준비는 6개 업무 화면**입니다 — `한눈에 보기 / 프로그램 준비 / 시간·장소 / 준비물·비용 / 담당자·할 일 / 현장 공유`. 단일 원천은 `PROGRAM_WORKSPACE_SECTIONS`이고 현재 화면은 URL 쿼리 `?workspace=`에 둡니다. 여러 프로그램을 가로지르는 일정·물품·업무 화면은 집계와 빠른 상태 변경을 제공하되, 이름·규칙·진행안 같은 상세 수정은 프로그램 원본으로 연결합니다. 프로그램 상세 안의 4개 섹션은 처음 온 스탭도 순서를 알 수 있게 `1 기획 시작 / 2 진행 순서 / 3 준비물·담당 / 4 확인·현장 공유`이며 `PROGRAM_SECTIONS`와 `?section=`을 씁니다. 목록 행은 내부 분류보다 지금 해야 할 한 가지 행동을 먼저 보여주고 그 입력 섹션으로 바로 엽니다. 두 탭 모두 방향키·Home·End 이동을 지원합니다. 본문 fieldset은 수동 초안 저장, 활동·역할·물품·할 일·회의는 하위 경로에 즉시 저장합니다. 진행 블록 일괄 붙여넣기는 TSV 미리보기를 거쳐 한 번의 root multi-location update로 추가하고, 행 순서는 `posts/{postId}/order`만 바꿉니다. ⚠ **본문 저장 payload에서 `tasks`·`meetings`·`posts`·`items`·`roles`·`competitionTeams`·`releases`·`activeReleaseId`를 반드시 제거**하세요 — 하나라도 남으면 다른 사람이 추가한 하위 항목이나 현장 배포본을 덮을 수 있습니다.
- **현장 공유는 변경 불가 배포본을 만듭니다.** 10개 현장 준비 기준과 실행 할 일이 모두 완료된 현재 원본을 `releases/{releaseId}/snapshot`에 저장하고 `activeReleaseId`·`status=published`와 함께 프로그램 노드 트랜잭션 한 번으로 확정합니다. 트랜잭션 안에서 `updatedAt`이 예상 버전과 같은지 다시 확인해 공유 직전 동시 편집도 과거 미리보기로 배포하지 않습니다. 이가드는 활성 배포본만 읽으며, 편집 원본을 이후 수정해도 다시 공유하기 전까지 현장 화면은 바뀌지 않습니다. 배포본 도입 전 `published` 데이터는 활성 배포본이 없을 때만 기존 방식으로 읽습니다. 미리보기와 실제 이가드 현장은 공용 `PublishedProgramCard`를 사용합니다.
- **준비 작업의 기본 단위는 활동 블록입니다.** 물품·역할은 `postId`로 게임·묵상·영상 등 해당 활동에 묶고 **입력은 활동 카드 안에서** 합니다. 수련회 전체의 `물품·비용`은 이 원본을 모아 주문·수령·포장·현장 도착, 담당·보관 위치, 예상·실제 지출, 정산을 보여줍니다. `postId`가 없거나 삭제된 활동을 가리키는 항목은 공통 묶음으로 거둬 데이터가 사라지지 않게 합니다. 준비율은 이름뿐 아니라 담당·수량·사전 점검·막힘의 실제 내용을 봅니다.
- **같은 사실을 두 번 받지 않습니다.** 준비물·스탭 역할의 단일 원천은 활동 카드의 `items`·`roles` 표입니다. 과거 자유 입력 값은 `PostLegacyText`가 읽기 전용으로 보여 이동할 때까지 감추지 않습니다. 행 단위 입력은 `ProgramAutosaveField`를 사용해 구독값과 사용자 입력의 충돌을 감지하고 저장 실패를 알립니다.
- **행 단위 입력은 `ProgramAutosaveField`만 씁니다.** uncontrolled `defaultValue`로 되돌리면 구독으로 바뀐 값이 화면에 반영되지 않고, 그 상태로 저장할 때 다른 사람이 방금 넣은 값을 과거 값으로 덮어씁니다. 편집 중 원격 변경이 오면 저장을 막고 최신 값을 알립니다. 행 삭제는 확인창 대신 되돌리기(`useProgramUndo` + `restoreRetreatProgram*`)로 같은 id 경로에 복구합니다. 이 세 계약은 `programInteractionContract.test.ts`가 지킵니다.
- 방학 중 사역 홈의 `새 수련회`는 항상 **수련회 목록 제목 옆**에 두고, 폼 가이드·PIN 잠금·현장 관리자처럼 목록 전체에 작용하는 도구는 `VacationHome.headerActions`를 통해 **화면 우측 상단**에 둡니다. 행정·현장 라우트가 이 위치를 따로 렌더링하지 않습니다.
- 준비 일정 캘린더는 `RetreatCalendarPanel` 하나로 통일했습니다(구 `PrepCalendar` 삭제). 수련회 기간 편집은 Rules상 행정 권한이 필요하므로 `canEditPeriods`로 잠급니다 — `prepMilestones`는 이가드팀도 공유 편집합니다.
- **새 색상 계열이나 강도(`*-200` 등)를 쓰기 전에 `globals.css`의 다크 재매핑 목록에 있는지 확인하세요.** 다크모드는 토큰이 아니라 `[data-theme="dark"] :where(.bg-*-50, …)` 규칙으로 Tailwind 팔레트를 눌러 바꿉니다. 목록에 없는 계열·투명도·강도를 쓰면 **그 자리만 밝게 남습니다**. 2026-08-16에 `fuchsia`·`rose`·`cyan`, 2026-08-21에 휴강용 `amber-50/60`과 반별 명단용 `blue/orange/red-200`이 실제로 이 문제를 일으켰습니다. 새 상태색은 배경과 글자를 한 쌍으로 추가하고 양 테마에서 대비를 실측하세요. 어두운 헤더의 작은 배지는 배경색 토큰 `--color-primary-light`가 아니라 `--color-badge-text`를 씁니다.
- 통합 브랜드 색: 학기·수련회 행정·이가드 모두 `globals.css`의 미드나이트 인디고·코발트·틸 토큰을 공유합니다. `.semester-scope`와 `.iguard-scope`는 배경·최소 높이만 제공하며 도메인별 원색으로 토큰을 재정의하지 않습니다. 상태 의미(정상·검토·위험)에만 에메랄드·앰버·로즈를 사용합니다.
- **수련회 PIN 잠금은 `useRetreatPinGate` 하나로만 판정합니다**(`src/features/portal/useRetreatPinGate.ts`). 잠금은 `retreats/{id}/iguard/accessLock` 한 노드에만 있으므로 **행정·이가드 어느 쪽에서 잠가도 양쪽이 잠깁니다**. 화면마다 구독을 새로 짜면 한쪽만 잠기는 사고가 납니다. 설정 UI는 공용 `AdminModal`(현장·행정 홈이 함께 씀), PIN 우회는 통합관리자만.
- **모달은 `aria-modal="true"`가 있어야 배경 스크롤이 잠깁니다.** `ModalScrollManager`(`providers.tsx`)가 OverlayShell이 아니라 **`[aria-modal="true"]` 존재 여부**를 MutationObserver로 보고 `body`를 고정합니다. 새 모달을 만들 때는 공용 `OverlayShell`을 쓰고(ESC·포커스 트랩·백드롭까지 함께 옵니다), 기존 모달을 손댈 수 없으면 최소한 `role="dialog" aria-modal="true" aria-label`을 붙이세요. 2026-08-16에 수련회 행정·이가드 모달 14곳에 이 속성이 없어 모바일에서 배경이 밀리던 것을 일괄 보강했습니다.
- **로드 실패 배너는 `useLoadErrors(scope)` 하나만 씁니다**(`src/lib/useLoadErrors.ts`). 실패를 경로별로 모아 **전부** 나열하고, `scope`(학기 id·계정 uid)가 바뀌면 렌더 중 파생으로 초기화합니다. 단일 `loadError` 문자열로 되돌리지 마세요 — 5개 구독이 동시에 거부돼도 마지막 하나만 보여 2026-08-08에 권한 공백의 원인을 두 번 잘못 짚었습니다. 저장·삭제 실패는 `actionError`로 분리합니다. ⚠ Firebase RTDB는 **한 번 거부된 리스너를 규칙이 바뀌어도 재시도하지 않습니다** — 권한을 열어도 그 탭은 새로고침(재구독) 전까지 실패 상태로 남습니다.

※ **화면 차단 ≠ 실제 차단.** `retreatsPrivate/*`는 Rules에서도 통합관리자·교역자·행정팀만 읽고 쓰도록 제한합니다. 역할 필드가 생기기 전 승인된 운영 계정은 기존 `role`을 하위호환으로 판정하며, `leader`와 이가드 계정은 차단합니다. 공개 `retreats/*` 등 나머지 경로는 아직 역할 버킷 단위 규칙이 있으므로 아래 화면 제한을 서버 권한으로 오해하지 않습니다.

- 사역팀의 "내 팀만 편집", 공개 수련회 쓰기 역할 세분화, 스탭의 `classes` 전체 읽기 차단은 후속 Rules 작업입니다.

**원칙: 화면에서 막는 것은 언제나 안전하지만, 화면에서 여는 것은 Rules가 허용할 때만 합니다.** (Rules가 막는 걸 화면에서 열면 "눌렀는데 실패"가 됩니다.)

- 행정 권한과 이가드 권한의 **쓰기 경계**는 계속 분리합니다. 이가드팀은 수련회 행정 명단을 조회할 수 있지만 저장은 현장 모듈의 허용 범위에서만 합니다.

## 인물 통합검색 계약

- 이름만으로는 동일인을 결합하지 않습니다. 학생은 정규화 이름·생년월일·부서·정상 진급선을 함께 사용합니다.
- 학생·교사·스탭 유형과 `person_student_*`·`person_teacher_*`·`person_staff_*` namespace를 보존합니다. 유형이 다르면 같은 실명·생년·연락처여도 별도 인물입니다.
- 학생은 같은 연도에 원본 ID가 다르면 항상 분리합니다. 다른 연도에서는 이름·생년월일·같은 부서가 일치하고 `학년 차이 === 연도 차이`인 진급 후보가 각 연도에 한 명뿐일 때 연결합니다. 본인 연락처의 변경·누락은 허용하고 보호자 연락처 하나만으로는 연결하지 않습니다.
- 영구 `personId`를 우선하되, 위 진급선이 유일하게 확인된 학생의 과거 분리 ID는 하나로 재연결합니다. 기존 연도별 학생·교사·스탭 ID와 출석·수련회·학기 참조키는 교체하지 않습니다.
- 학기 신청의 `personId`는 같은 연도 `studentId`가 가리키는 공식 학생·스탭 원장의 값을 복사합니다. 이름만 같은 신청에는 부여하지 않습니다.
- 수련회 단체티처럼 식별자가 없는 보조 기록만 같은 행사·같은 유형의 유일한 기준 레코드에 제한적으로 연결합니다.
- 대표 이름은 최신 연도 출석부 학생 이름을 우선합니다. 수련회 명단에서 유입된 `134 이예원` 같은 앞자리 순번은 검색 별칭에서 제거해 표시하고, 수련회 원본·백업 데이터는 수정하지 않습니다.
- 인물 상세는 카테고리 탭 대신 최신 연도부터 연도 탭으로 묶습니다. 학적·출석, 학기 사역, 새친구, 수련회 정보는 해당 연도 안에서 함께 보이되 `현장 등록` 보조 기록은 통합검색에 표시하지 않습니다.

## 실시간 읽기 계약 (2026-08-13)

- 화면에 계속 표시되는 Firebase 목록·상세 데이터는 `onValue` 또는 `onChild*` 구독을 사용하고, 컴포넌트가 닫히거나 대상 ID가 바뀔 때 반드시 unsubscribe합니다. 출석부 원장 `classes/{year}`·`attendance/{year}`, 학기 `semesters/*`, 수련회 `retreats/*`와 관련 명단·배정·운영 탭이 이 계약에 포함됩니다.
- 이가드 `IguardClient`의 workspace는 `key={id}`로 수련회 ID가 바뀔 때 상태를 새로 시작합니다. `useRetreatData`는 metadata의 `id`가 현재 ID와 일치할 때만 해당 `year`로 데이터 구독을 시작하고, 해제된 metadata·연결·데이터 구독의 성공·오류 콜백이 상태나 workspace 캐시를 갱신하지 못하게 합니다. 같은 수련회의 이름·날짜나 현장 뷰 변경을 workspace key에 넣어 구독을 다시 열지 않습니다. metadata 조회 실패는 실제 수련회 없음과 구분해 화면에 오류로 표시합니다.
- `PortalHome`과 `useMyPageData`의 전체 기간 구독은 수련회 객체 배열 대신 **순서를 보존한 ID 목록**에 의존합니다. 이름만 갱신되어도 제목은 새로 표시하되 기간 구독은 유지하고, ID 추가·삭제·순서 변경에는 다시 구독합니다. 같은 날짜의 기간 선택은 기존 목록 순서를 사용하므로 ID를 정렬해서는 안 됩니다. 마이페이지의 현장 데이터 구독도 수련회 객체 대신 현재 `id`에 의존합니다.
- 인물 통합검색은 검색창이 열린 동안에만 권한이 허용한 루트를 구독합니다. 각 루트는 최상위 child 추가·변경·삭제분을 병합해 한 경로 변경 때문에 전체 루트를 다시 받지 않도록 하고, 검색창을 닫으면 전부 해제합니다.
- 인증·권한 판정, 저장/삭제 직전 최신값 확인, 백업·복구, 멱등성 검증, 버튼으로 실행하는 외부 시트 가져오기는 일회성 `get`을 유지합니다. 이 조회는 화면 캐시가 아니라 거래 안전과 명시적 명령의 일부입니다.
- 구독 화면에서 저장 성공 뒤 배열에 같은 항목을 수동 append하지 않습니다. Firebase echo가 같은 항목을 다시 전달해 중복 표시될 수 있으므로 표시 상태는 구독 콜백을 단일 원천으로 둡니다. 입력 중 초안·드래그 배정처럼 로컬 편집 보호가 필요한 화면은 기존 dirty/ref 충돌 방지를 유지합니다.
- 이 전환은 읽기 방식만 바꾸며 DB 경로·데이터 구조·Rules를 바꾸지 않습니다. 출석부 앱이 `classes`를 저장하면 RTDB 값이 먼저 바뀌고, 열린 통합사이트 구독 콜백이 그 변경값으로 화면 파생 결과를 다시 계산합니다.

## 학기 사역 계약 (2026-08-06)

- **접수 원칙**: 훈련(`trainingClassId`)을 신청해야 사역팀(`choice1`)에 지원할 수 있다. 예외는 **고3 2학기와 스탭**. 판정은 `features/semester/intakeRule.ts`(순수)만 사용하고 화면에서 조건을 재구현하지 않는다.
- `trainingOnly`는 계속 저장하되 `deriveTrainingOnly`로 파생한다 — 출석·수료 명단(`roster.ts`)이 쓰는 기존 계약이라 직접 세팅하지 않는다.
- **훈련 명단**은 훈련 반 배정자 전원이다(사역팀을 겸하는 사람 포함). 레거시 `trainingOnly=true`도 훈련 신청으로 흡수한다.
- **회차 유형**은 `sessionKind.ts`로만 변환한다. 선택지는 `개강`·`종강`·`휴강`·`직접 입력`이고 신규 기본값은 `직접 입력`이다. 개강·종강·휴강은 `훈련&사역팀 …` 표준 문구로 표시하며 레거시 짧은 라벨도 화면에서 정규화한다. 저장 스키마(`type`/`label`)는 그대로이고, **출석 집계(만점)에서 빠지는 것은 `휴강`뿐**이다(`completion.regularSessions`).
- **1박 2일 이상의 회차**는 기존 `date`를 시작일로 유지하고 같은 회차에 선택 필드 `endDate`를 붙인다. 출석·커리큘럼 키는 계속 회차 `id` 하나를 사용해 날짜 수만큼 중복 집계하지 않는다. 날짜 검증·표시는 `sessionDate.ts`, 저장 시 종료일 삭제는 `updateSessionDates`가 담당한다.
- 훈련 반 삭제는 `trainingClass.ts`의 루트 다중 경로 update로 신청자 참조까지 함께 정리한다(팀 삭제와 같은 패턴).
- **학기 삭제**(`removeSemester`)는 `semesters/{sid}`와 `semestersPrivate/{sid}`를 한 번의 루트 update로 지운다. 되돌릴 수 없으므로 화면에서 **학기 ID를 직접 입력받아** 확인한 뒤에만 호출한다.
- **수련회 생성**은 행정·이가드 공용 컴포넌트 `features/portal/NewRetreatButton.tsx` 하나만 쓴다. `retreats/{id}`가 공유 노드라 어느 화면에서 만들어도 양쪽 목록에 나타난다. 쓰기는 행정 db(`@/lib/db`)가 담당하고 버튼은 `canEditPortalArea("retreat-admin")`로 게이트한다.
- **화면에서 교사·스탭은 학생과 섞지 않는다.** 스탭은 훈련·지망·보호자 연락처가 모두 없어 읽는 항목 자체가 다르고, 팀마다 고정으로 붙어 있어 같이 나열하면 학생 현황이 묻힌다. 신청 탭 접수 명단은 스탭을 **접힌 그룹**으로 따로 두고(기본 접힘), 배치 탭 팀 카드는 명단에 학생만 두고 스탭은 **카드 헤더 우측 토글**로 펼친다(한 번에 하나만). 구분은 `splitStudentsAndStaff`/`isStaffApplication` 하나만 쓴다. 명단 상세 모달도 스탭 칸을 접어서 연다(학생 칸은 항상 펼침). 단 **학생이 없는 팀은 스탭을 펼친 채로 연다** — 접어 두면 모달이 빈 채로 열려 고장으로 보인다. 같은 이유로 "학생 이름을 누르면…" 안내는 학생이 있을 때만 띄운다.
- **교사·스탭 접수**는 학생과 다른 경로다: 훈련·지망 없이 사역팀에 바로 배정한다(`intakeRule.isStaffApplicant`). 저장 시 `teamId`를 직접 채우고 `choice1/2`·`trainingClassId`는 비운다.
- **배치·커리큘럼은 두 축**이다: 사역팀(`teams`)과 훈련 반(`trainingClasses`). 커리큘럼은 `curriculum/{id}` 한 맵을 공유한다(두 축의 id가 겹치지 않는다). 훈련 반에는 `goal`이 없으므로 학기 목표 박스는 사역팀에서만 보인다.
- **홈 공유 캘린더**의 "공유 일정"은 `prepMilestones`다. 추가·수정·삭제는 Rules와 같게 스탭을 제외하고 열어 둔다(`canEditPortalArea("retreat-admin") || iguardScope === "all"`).
- **사역 가이드**의 기본값은 `features/ministryGuide/ministryGuideContent.ts`의 정적 운영 원칙이다. 권한 있는 담당자의 월별 흐름·부서 운영 가이드 수정본은 기존 공유 경로 `prepMilestones/*`에 `sourceSite=ministry-guide*`인 결정적 레코드로 나눠 저장하고, 일반 일정 구독은 이를 반드시 필터링한다. 연간 계획은 `가안`으로 표시하며 학생 실명·연락처·주소·가정·건강 특이사항과 미결 아이디어는 넣지 않는다.
- **주일 사역의 새친구 탭**은 학기 선택 없이 모든 `semesters/*/newFriends`를 통합 조회한다. 기존 학기별 기록은 이동하지 않고, 신규 기록만 학기가 아닌 연도별 내부 작업공간 `semesters/{year}-sunday/newFriends`와 `semestersPrivate/{year}-sunday/newFriendsPrivate`에 저장한다. 이 작업공간은 `meta`를 두지 않아 학기 목록에 나타나지 않는다. 행정팀은 접수·2주 과정·등록 결정·반배정을 관리하고, `classes/{year}` 반영·삭제·등반 취소는 `canWriteStudentRoster(roles)`가 참인 통합관리자·행정팀만 실행한다. 수정 가능한 접수일은 `registeredDate`(한국 기준 `YYYY-MM-DD`)로 저장하며, 감사 시각 `createdAt`은 변경하지 않는다. 기존 레코드에 접수일이 없으면 화면에서 `createdAt`의 한국 날짜를 사용한다. 이 함수는 새친구 ID 기반 결정적 학생 ID, 중복 차단, 대상 반 확인, 비공개 사전 스냅샷, 단일 학생 경로+반영 이력의 원자 update와 재조회 검증을 유지한다. `removeNewFriendFromRoster`는 결정적 `nf_` ID·현재 이름·연결 반을 재검증하고 학생·해당 출석·새친구 공개/비공개 기록을 원자 삭제한다. 삭제 직전 전체 사본은 `newFriendRosterBackups/{friendId}/removals/{timestamp}`에, 학생 복구 사본은 `trash/{year}/students/{backupKey}`에 남기고 결과를 재조회한다. 일반적인 `classes`·`attendance` 쓰기 함수로 넓히지 않는다.
- **행정 변동 사항 탭**은 학생 앱 소유 `classes/{year}/{classKey}/adminChanges`를 읽기만 한다. 학생 앱이 학생 명단 수정과 같은 원자 update로 만든 감사기록이며, 통합 앱에서는 생성·수정·삭제하지 않는다. 기존 `변경 이력`은 제거하고 `학생 변동`은 `등록 현황`으로 표시한다.
- **새친구 완료 기준은 출석부 반영(`rosterSync`)**이다. `giftDate` 입력은 운영 화면에서 제거했으며 신규 저장에 사용하지 않는다. 다만 과거 `giftDate`가 있는 레코드는 완료로 계속 읽고 일반 수정으로 값을 지우지 않아 별도 DB 마이그레이션 없이 보존한다. **등반 및 배정 취소**는 새친구 공개·비공개 기록과 등록 결정·2주차 기록을 보존하고 `assignedClassKey`·레거시 `giftDate`·`rosterSync`를 해제해 `반배정` 단계로 되돌린다. 출석부 반영 후에는 `canWriteStudentRoster(roles)` 허용 역할만 실행하며, 결정적 `nf_` 학생·해당 출석을 사전 백업과 `trash`를 남긴 뒤 원자적으로 제거한다. 새친구 기록까지 지우는 `명단·출석부 삭제`와 구분한다.
- **새친구 목록 검색**은 이름·학교·바나바 담당·부서/학년·등록 결정·배정 반·날짜를 여러 단어로 함께 찾는다. 본인/보호자 연락처는 수정 권한이 있을 때만 검색하며 비공개 메모·주소는 검색하지 않는다. 원본 학생 객체와 `storageSid:id` 키를 유지해 다른 학기의 같은 ID를 잘못 수정하지 않으며, 상단 단계 집계·반배정 대기 목록은 전체 기준을 유지한다.
- 큐싯 **구글 시트 연동은 2026-08-07 제거**했다(표 붙여넣기만 사용). `iguard/cueSheet` 노드와 db 함수는 남아 있지만 화면에서 쓰지 않는다 — 되살릴 때만 참고한다.
- **인원체크 키에 배열 인덱스를 넣지 않는다** — `checklistKeys.ts`의 `stableMemberId`(`{kind}:{ownerId}:{name}`)만 쓴다. 인덱스를 넣으면 행사 중 한 명이 불참 처리될 때 뒤 사람들의 체크가 통째로 어긋난다. 운영 DB에는 구형 인덱스 키가 남아 있으므로 판정·해제는 반드시 `memberCheckKeys`/`isMemberChecked`를 거친다(신형·구형 동시 인식, 쓰기는 신형만).

- **전체 덮어쓰기는 사전 백업 성공을 확인한 뒤에만** — 상시 저장과 복구 모두 `backupNodeBeforeOverwrite`의 반환값을 검사한다(`if (!backedUp) throw`). 최근 백업이 있으면 헬퍼가 성공으로 처리한다.
- **출석 표**(`AttendanceGrid`)의 셀은 토글이 아니다. 셀을 누르면 출석·지각·결석·지우기를 명시적으로 고른다(멱등 기록 — 실수 규칙 11). 상태 메뉴 좌표는 클릭한 셀에서 즉시 계산하고 닫을 때 좌표도 비워 이전 셀의 흰 메뉴가 한 프레임 튀지 않게 한다.
- `.input`은 `@layer` 밖 규칙이라 `width:100%`가 유틸리티 `w-*`를 이긴다. 폭은 감싼 div로 주고, 높이는 `h-*`로 고정하지 않는다(모바일 16px 글꼴에서 글자가 잘린다).

`/sunday-ministry/praise`는 `src/features/praise`의 다섯 업무 탭을 사용한다. `src/app/api/praise`의 Node 서버가 Firebase ID 토큰의 폐기 여부와 현재 두 축 역할을 확인하고, 조 담당 권한·revision·작업 ID를 검사한 뒤 `praiseOps/{workspaceId}`를 갱신한다. 새 별도 Firebase 로그인 구독을 만들지 않는다. 운영 기간·탭·회차는 `workspace`·`tab`·`meeting` 쿼리로 보존한다.

- 찬양 운영 개설은 공통 학기·사역팀 선택을 기본으로 하고 학기에 속하지 않는 별도 기간만 명시 예외로 둔다. 새 운영 공간의 토요 모임은 날짜가 정확히 같고 유일한 학기 회차만 자동 연결한다. 사람은 `rosterLink.applicationKey`를 명시 선택해야 하며 이름·날짜 유사도로 기존 이관본을 자동 연결하지 않는다. 찬양 인물의 기존 `id`·`sourceId`·`kind`는 과거 출결·조·등단 참조이므로 유지한다.
- `rosterLink`는 배치된 학기 신청과 공식 `classes/{year}` 또는 `teacherStaff/{year}`의 같은 `personId`가 확인된 경우만 저장한다. 이 대조에서 `semesters/{sid}/applications`·`classes`·`teacherStaff`는 읽기 전용이며, 찬양 화면이 명단을 맞추기 위해 해당 원장을 생성·수정하지 않는다. 기존 연결은 해제·교체하지 않고 누락된 동일인 필드만 보완한다.
- 차단 항목이 남은 `shadow`에서는 관리자의 기존 팀원 `person.reconcile`만 허용한다. 출결·등단·조편성·가져오기·새 팀원 등록과 차단 항목/모드 변경은 계속 잠그며, 일반 `person.save`로 우회하지 못하게 서버가 기존 인물·shadow 상태를 재검증한다. 여러 확정 연결은 한 workspace transaction으로 인물 revision·작업 영수증·한국어 감사를 함께 저장한다.
- 출결은 PRESENT/ABSENT이며 미입력은 null이다. 연결된 회차와 신청자는 `semesters/{sid}/attendance/team/{sessionId}/{applicationKey}`를 공통 원장으로 조회·수정하고 찬양 출결 화면과 등단 계산이 같은 값을 사용한다. `지각` 레거시는 PRESENT로 읽되 새 저장은 `출석` 또는 `결석`만 쓴다. 연결되지 않은 기존 이관 기록은 `praiseOps`의 조회용 fallback으로 보존한다.
- 공통 출결 저장은 workspace에 작업을 먼저 예약하고 `semesters/{sid}` transaction 안에서 최신 학기·팀·회차·신청 배치를 다시 검증한 뒤 출석 셀과 `praiseOperationReceipts/{receiptHash}`의 `applied` 표식을 함께 저장한다. 표식에는 phase·요청 지문·처리 시각만 두고 UID·이름·회차/신청키·경로를 넣지 않으며 덮어쓰기·자동 삭제하지 않는다. 서로 다른 workspace와 학기 원장을 단일 원자 커밋으로 설명하지 않는다.
- 저장 응답이 불확실한 요청은 일반 재시도로 출석을 다시 적용하지 않는다. 관리자 검토도 외부 표식보다 먼저 private workspace에 최신 권한·원본 요청·작업 번호를 `prepared`로 예약한다. 영구 `applied` 표식이 확인될 때만 원래 감사를 완료하고, 표식이 없고 현재 출석 revision을 직접 확인한 경우에만 원장 변경 없이 `closed`로 종료한다. 외부 증거 뒤에는 예약을 `verified`로 바꾸고 감사 완료까지 재시도하며 다른 관리자가 먼저 완료한 예약은 `superseded`로 닫는다. 늦게 도착한 저장은 두 표식 모두에서 중단한다.
- 일반 담당자는 원본 출결을 담당 조 범위에서만 읽고 쓴다. `import-unresolved` 등 과거 조가 검증되지 않은 기록은 운영자만 확인한다. 학기 신청키·Firebase 경로·다른 조의 출결은 API 응답에 노출하지 않는다.
- 확정 조·등단은 새로운 불변 버전이다. 초안의 수정은 새 버전으로 저장하며, 같은 주일의 최신 확정본만 이후 등단 빈도 계산에 사용한다. 회차 날짜가 바뀌어도 과거 버전의 `worshipDate`를 다시 계산하지 않는다.
- 공통 출석을 쓰는 회차의 등단 생성·저장·확정은 workspace ETag를 읽어 계산하고, 저장 직전에 같은 회차의 출석·연결 근거를 다시 읽은 뒤 `If-Match`로 저장한다. 412 충돌은 최신 workspace로 계산과 외부 검증을 모두 반복한다. 마지막 외부 검증과 workspace PUT 사이의 학기 원장 변경까지 묶는 분산 원자성은 없으므로 다음 조회에서 최신값을 다시 반영한다.
- `server/roster.ts`는 기존 학기 배치·훈련 예외 계약을 재사용하고 신청키로 인물을 명시 연결한다. 신청과 공식 학생·스탭 레코드의 이름·유형·`personId`를 함께 검증하고 원장 연락처·메모를 API에 복제하지 않는다. 공통 학기 사역팀 출석 셀 외의 기존 학생·스탭 원장에는 쓰지 않는다. 동일인 근거가 부족하거나 학기 배치가 없는 인물은 자동 연결하지 않고 관리자 확인 대상으로 남긴다.
- `node scripts/run-praise-contracts.mjs`는 저장소 루트에서 실행한다. 실제 운영 자격정보를 사용하지 않는 demo-praise RTDB 에뮬레이터 계약 검사이며 Java 21이 필요하다.

- **접근법**: `PortalHome.tsx`의 `roleError` 화면을 `AuthContext.tsx`의 네 권한 조회로 추적한다 → 운영 Rules의 `admins/{uid}` 일반 계정 거절을 확인한다 → Firebase SDK의 실제 `get()` 거절 문구 `Permission denied`와 판정식을 대조한다 → `AuthContext.render.test.tsx`에서 공백형·밑줄형 응답을 모두 검사한다.
- **판단 질문**: 두 계정의 팀 배정을 다시 쓰거나 Rules에서 일반 계정에 `admins`를 열지 않는다. 예상된 거절은 관리자 여부만 `false`로 처리하고, 연결 실패는 계속 전체 권한 조회 오류로 남긴다.
- **재사용 규칙**: 여러 일반 계정에서만 역할 로딩이 실패하면 `get()` 오류의 `code` 유무와 실제 `message` 형식을 확인한다. 모의 테스트의 `permission_denied`만 근거로 운영 SDK 응답 형식을 가정하지 않는다.

### 경로별 실패 복구와 표시 기간 일치 (2026-10-05)
- **접근법**: `useLoadErrors`의 경로별 오류 맵을 사용해 필수 명단·회차 오류와 연락처 오류를 구분한다 → 실패 콜백도 준비 완료로 표시하되 필수 실패에는 입력기를 열지 않는다 → 다시 불러오기는 계정·권한·팀·학기 키를 가진 내부 화면을 재생성해 거부된 RTDB 구독을 실제로 다시 연결한다 → `semesterSummaryMeta`로 메타 기간이 없는 학기의 실제 회차 범위를 표시용으로 계산하고 홈·행사·프로그램 기본 수련회는 `selectRetreatForWork`를 공유한다.
- **판단 질문**: 다른 구독 하나가 성공했다고 모든 오류를 지우거나 연결 실패를 빈 명단으로 표시하지 않는다. 회차에서 파생한 기간은 목록 표시이며 운영 DB 날짜를 자동 보정하지 않는다. 휴강은 공유 달력에 남기고 홈 업무와 다음 모임 추천에서만 제외한다.
- **재사용 규칙**: 필수 원장 실패는 입력 차단, 부가 정보 실패는 사용 가능한 영역 유지, 재시도는 재구독, 성공은 같은 경로의 오류만 해제한다. 기본 기간 선택과 명시 기간 선택을 분리하고 도메인 왕복에서는 실제 ID와 학기를 함께 유지한다.


### 학기 목록은 원장 전체 대신 ID·메타만 구독하기 (2026-10-05)
- **접근법**: `semesterList.ts`에서 `/api/semester-ids`의 인증된 shallow 탐색으로 키만 얻는다 → 학기별 `meta`만 실시간 구독하고 기간이 하나라도 비어 있으면 `sessions`를 추가한다 → 동일 UID 소비자가 하나의 구독을 공유하며 마지막 소비자가 해제되면 요청·타이머·구독을 모두 정리한다 → 생성·삭제 성공 후, 화면 복귀·온라인 복구 및 보이는 화면의 1분 주기로 ID만 갱신한다.
- **판단 질문**: `onChildAdded(semesters)`도 학기 원장 전체를 내려받으므로 최적화로 사용하지 않는다. 별도 목록 인덱스·운영 DB 이관을 만들지 않고 기존 경로를 보존한다. 토큰은 API/서버 REST 헤더에만 넣고 서버는 폐기 검사·최신 역할로 승인한다. 조회 실패를 빈 목록으로 변환하지 않는다.
- **재사용 규칙**: 화면 갱신 억제와 전송량 감소는 다른 문제다. 루트의 큰 자식 목록은 shallow ID 탐색과 필요한 하위 경로 구독으로 분리하고, 기간 추정·오류 복구·계정 변경·동적 추가/삭제를 함께 검증한다.


### 메뉴 표시와 데이터 접근을 분리하고 재시도 이전 응답을 차단하기 (2026-10-06)
- **접근법**: `GlobalPortalHeader`, `TeamsHome`, `OperationsHome`, `RetreatAreaNav`와 상세 탭을 정적 메뉴로 표시한다 → 같은 capability로 ‘권한 필요’와 허용 대상 prefetch를 판정한다 → `WorkspaceAccessGate` 안에서만 보호된 컴포넌트를 마운트하고 데이터 구독에는 로그인·역할 확인·권한 조건을 둔다 → 재시도는 attempt/generation으로 실제 구독을 교체하며 cleanup의 active/alive fence로 이전 성공·실패 콜백을 차단한다.
- **판단 질문**: 메뉴를 보이게 하기 위해 `accessPolicy.ts`, `teamModel.ts`, Firebase Rules 또는 API 권한을 넓히지 않는다. `useLoadErrors.ok()`의 과거 scope 콜백이 현재 오류를 지울 수 있으므로 화면에서 이전 리스너의 결과를 먼저 차단한다. 프로그램 입력기 전체를 재시도마다 초기화하면 초안이 사라지므로 연결 generation과 계정·권한·수련회 scope를 분리한다.
- **재사용 규칙**: 업무 이름은 공개하고 내용·구독·명령은 기존 권한으로 보호한다. 오류는 빈 데이터와 구분하고, PIN 오류는 pending보다 먼저 처리하며, 실제 재연결은 초안 보존과 이전 응답 차단을 함께 검증한다. 홈도 역할 확인 완료(`user && !loading && !roleError`) 후에만 구독·담당 팀 자동 이동을 실행하고, 재시도 이전의 성공·실패 콜백은 cleanup fence로 차단한다. 업무 진입은 `HomeStart` 한 곳에 두고 오늘 확인할 일·미래 일정·펼치는 전체 달력을 구분한다.
