## 수정하지 않은 문제와 후속 제안

1. **P1 / F06·F07, `attendance-app/database.rules.json`**: 역할 버킷 전체 권한과 adminTeam의 임의 학생 leaf 쓰기는 남아 있다. 최신 사용자 지침의 “Rules 변경 필요성은 보고만 한다. 직접 수정·배포하지 않는다”를 따른다. 역할별 허용/거부 매트릭스를 에뮬레이터로 검증한 뒤 Rules 담당자가 반영해야 한다. 새친구 예외는 서버에서 ID 토큰·역할·새친구·반·출석을 재확인하는 좁은 단건 API로 이관하고 클라이언트 직접 쓰기 예외를 제거하는 방안을 권한다.
2. **P1 / F04, `attendance-app/src/lib/sheetSyncCommit.ts`**: 같은 UID의 다른 탭은 기존 Rules상 자기 잠금을 통과한다. 마지막 조회와 PATCH 사이, 이전 오프라인 큐, 지연된 요청까지 완전히 막으려면 모든 명단/출석 쓰기의 버전·불변 작업 표식 계약이 필요하다. Firebase REST PATCH는 If-Match를 지원하지 않으므로 헤더 추가만으로 해결할 수 없다. 결과 불명확 잠금은 관리자 원장 확인 없이 자동 해제하지 않는다.
3. **P1 / 휴지통 키 충돌, `attendance-app/src/components/modals/StudentModal.tsx`**: 반 범위 SID를 `trash/{year}/students/{sid}`에 저장하므로 서로 다른 반의 같은 SID 삭제본이 충돌한다. `DB_OWNERSHIP.md` 학생/반/출석 표의 trash 행에 따라 통합 앱 새친구 되돌리기도 소비한다. 반·작업 ID를 포함하는 키와 양 앱 읽기 호환 변경은 공유 계약 확인 후 별도 반영해야 한다. 기존 운영 데이터를 이관하지 않았다.
4. **P2 / 새친구 동시 수정**: rosterSync 삭제는 방지했지만 사전 GET 이후 동일 필드 동시 수정의 마지막 쓰기 우선 동작은 남는다. 공개·비공개 루트의 조건부 원자 저장은 신뢰 서버 또는 별도 버전 Rules 계약이 필요하다.
5. **인증 E2E 미확인**: 운영 로그인은 알림 확인 자동 쓰기를 일으킬 수 있다. 이번 작업에서는 운영 인증 화면 E2E를 실행하지 않는다. 저장된 로그인 파일 존재·버전 응답을 인증 화면 성공으로 간주하지 않는다. PR 인증 QA는 별도 비운영 Firebase/전용 계정을 마련한 뒤 추가해야 한다.
6. 통합 앱의 운영 의존성 감사는 0건이며, Lighthouse 개발 도구의 전이 취약점 15건은 남아 있다. 파괴적인 강제 다운그레이드는 적용하지 않았다.
