# 찬양팀 운영 기능의 고등부 통합사이트 통합 기획안

2026-09-06 · 소스 전체 구조 및 업무 흐름 검토 · 구현 전 기획

**권고: 기존 통합사이트의 ‘주일 사역 → 찬양팀’을 주간 운영 공간으로 완성한다.** 외부 앱의 조 편성·등단 배정 로직을 재사용하고, 로그인·학기·인물 연결·관리자 활동 로그는 통합사이트에 맞춘다. 사용자가 실제 운영 기록이 쌓여 있다고 확인했으므로, 기존 앱을 운영하면서 이관본을 대조한 뒤 입력 창구를 전환한다.

이 문서는 승인된 구현의 기준이 된 당시 기획안이다. 아래 검토 시점에는 운영 DB 조회·변경, 계정 변경, Rules 수정·배포, 앱 구현·배포는 하지 않았다. 실제 운영 데이터의 건수·품질과 외부 사이트의 배포 상태는 확인하지 않았다.

## 1. 무엇을 읽었는가

외부 저장소는 최신 구현과 이전 구현, 모임 콘텐츠가 함께 있는 구조다. 기능 판단은 README만 따르지 않고 실제 화면·API·도메인 로직·SQL을 대조했다.

| 검토 범위 | 확인한 내용 | 통합에서의 의미 |
|---|---|---|
| worship-admin-v2 · 117개 파일 | Next.js, Supabase 인증·Postgres·RLS·비공개 파일 저장, 학기·명단·출결·조 편성·등단·이력 | 업무 로직을 가져올 주된 기준 |
| staff-guide-site · 78개 파일 | 이전 Next/vinext·Cloudflare D1/R2 구현, ChatGPT Sites 인증 연결, 기존 운영 화면 | 요구사항·운영 예외 비교용. 인증·DB 런타임은 이식 대상에서 제외 |
| docs 및 루트 안내 · 3개 파일 | 제품 사양, 운영 지침, 저장소 구성 | 문서와 실제 구현 차이 확인 |
| 나눔마블 자료 · 29개 파일 | 편집형 PPTX 21장, 진행문, 보드·슬라이드 PNG, 미리보기·검수 자료 | 첫 모임 자료실과 가이드 템플릿으로 활용 |

총 227개 파일의 목록을 확인했다. 업무 코드·화면·API·권한·SQL·문서는 내용 중심으로 읽었고, lockfile·생성된 스냅샷은 구조를 확인했다. PPTX는 슬라이드 텍스트와 구조, 기존 몽타주·보드 이미지를 확인했다. 모든 바이너리를 새로 렌더링하거나 외부 코드·테스트를 실행한 검토는 아니다. 파일별 검토 목록은 기획 산출물의 reading-manifest.json에 별도로 보존했다.

외부 기준 커밋은 [982dc53](https://github.com/andew423-source/high-school-worship-team/tree/982dc53ab3ee6d1261736167e5a000deec07974b)이다. 통합사이트는 원격 main 4124ded를 기준으로 비교했다. 작업 중 확인한 운영 buildId는 68f7bef이며, 두 커밋 사이 앱 코드 차이는 없고 배포 기록 문서만 추가된 상태였다. 사용자의 기존 로컬 변경은 보존했다.

## 2. 이 사이트의 중심 기능

이 프로젝트의 중심은 ‘곡목·악보 관리’보다 **토요모임 출결을 바탕으로 주일 등단을 준비하는 업무**다.

~~~mermaid
flowchart LR
    A[학기·팀원·모임 준비] --> B[조 편성 초안·수정·확정]
    B --> C[토요모임 출결 입력]
    C --> D[주일 등단 후보 검토]
    D --> E[자동 배정·수동 조정]
    E --> F[확정본·PNG·PDF]
    F --> G[학생별 등단 이력]
    G --> D
~~~

| 기능 | 실제 구현 | 통합 판단 |
|---|---|---|
| 학기·일정 | 학기 생성, 토요일 생성, 활성·보관, 휴강·임시 모임 | 통합 학기와 연결하고 찬양팀 모임 속성만 확장 |
| 팀원 | 학생 기본 정보와 학기별 속성 분리, 스탭, CSV/XLSX 미리보기·열 매핑·검증 | 기존 인물 연결을 우선하고 가져오기 검증을 재사용 |
| 조 편성 | 정원·성별·학년·역할·함께/분리 조건, 자동 학생 편성, 드래그 수정, 스탭 수동 배정, 확정 버전 | 순수 알고리즘과 검증 로직 재사용 가치 높음 |
| 토요 출결 | 담당 조, 학기 전체 표, 미입력·출석·지각·결석, 휴강 잠금, 저장 충돌 검사 | 기존 사역팀 출석과 같은 행사인지 먼저 판정 |
| 주일 등단 | 1·2부 싱어/콰이어, 인도자, 스탭 참석, 스탭만 등단 모드, 등단 제외·강제 배정·부서 이동 | 찬양팀의 핵심 신규 기능으로 도입 |
| 편집·공유·이력 | 등단 배치 수정, 초안/확정본, PNG/PDF, 학생별 최신 확정 등단 이력 | 과거 확정본을 보존하면서 도입 |
| 모임 가이드 | 첫 회차 가이드 중심, 이후 회차는 준비 중 | 회차별 템플릿으로 보완 |
| 콘티·곡목·악보·연습자료 | 독립적인 관리 UI/API는 확인되지 않음 | 새 요구사항으로 분리. 기존에 있는 기능처럼 견적·일정에 넣지 않음 |

근거: [v2 구조](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/docs/architecture.md), [조 편성](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/src/domain/grouping.ts#L172), [등단 배정](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/src/domain/stage.ts#L144), [학생별 등단 기록](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/src/domain/stage-records.ts).

## 3. 통합 방식 비교와 권고

| 방식 | 얻는 것 | 비용·제한 | 권고 |
|---|---|---|---|
| 외부 사이트 링크 연결 | 현재 운영을 빠르게 유지 | 별도 로그인·명단·권한·기록이 계속 남음 | 이관 기간의 임시 진입점 |
| 통합 UI + 기존 Supabase 유지 | 현행 SQL·실제 데이터 유지 | 인증 연결, 두 DB의 인물·학기 대응, 감사·장애·백업 운영을 계속 관리해야 함 | 이관 검증에서 SQL 재구현 부담이 큰 경우의 대안 |
| 통합 UI + 현재 Firebase 중심 모듈 | 기존 로그인·권한·학기·관리자 로그에 일관되게 연결 | SQL 트랜잭션·버전·충돌 처리와 데이터 이관을 다시 설계해야 함 | **목표 구조로 권고** |

현재 통합사이트에는 이미 /sunday-ministry/praise와 praise 역할이 있고 메뉴만 기획 상태다. 기존 ‘예배팀’은 worship, ‘찬양팀’은 praise이므로 두 메뉴를 합치지 않는다. 외부 저장소 이름의 worship을 현재 예배팀에 대응시키면 업무가 잘못 연결된다. [기능 카탈로그](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/features/portal/featureCatalog.ts#L31), [역할 정책](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/features/portal/accessPolicy.ts#L154).

실제 운영 기록이 있다는 점 때문에 Firebase 이관을 즉시 시작하는 것은 권하지 않는다. 먼저 **원본 스냅샷 복원·ID 연결·핵심 저장 계약 검증**을 진행하고, 그 결과를 기준으로 최종 저장 방식을 확정한다. 이 검증이 실패하면 Supabase 유지 대안을 비교하되, 두 DB에 같은 출결을 동시에 쓰는 임시 구조는 만들지 않는다.

Google 계정이 같아도 Supabase 사용자 ID와 Firebase UID는 동일하지 않다. 기존 Firebase AuthContext를 유지하고 실무 스탭과 로그인 계정을 명시적으로 연결한다. 기존 외부 관리자 계정을 통합관리자로 자동 승격하지 않는다. [외부 인증](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/src/lib/auth.ts), [현재 인증](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/context/AuthContext.tsx), [현재 역할 배정](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/features/portal/roleAssign.ts#L36).

## 4. 제안하는 화면 구성

진입 경로는 **로그인 → 주일 사역 → 찬양팀**이다. 마이페이지에는 ‘이번 모임 출결’과 ‘이번 주 확정 등단표’ 바로가기를 보여준다. 별도 찬양팀 관리자 로그인을 만들지 않는다.

| 탭 | 첫 화면과 주요 작업 | 대상 |
|---|---|---|
| 이번 주 | 모임 날짜·휴강 여부, 내 담당 조 미입력, 등단 준비 단계, 최신 확정본, 모임 가이드 | 모든 찬양팀 사용자. 역할별로 할 일만 다르게 표시 |
| 출결 | 기본은 선택한 모임·내 조, 학생 검색, 명시적 상태 선택, 저장 상태. 학기 전체 표로 전환 | 조 담당 스탭·운영자 |
| 등단 | 예배 날짜·1/2부, 후보와 제외 사유, 자동 배정, 수동 조정, 확정, 내보내기, 과거 확정본 | 편성 담당자는 편집, 일반 스탭은 확정본 조회 |
| 팀원·조 | 학생·스탭 검색, 소속·역할 필터, 찬양 전용 정보 수정, 조 편성·확정, 담당 계정 연결 상태 | 운영자 중심 |
| 운영 설정 | 학기 연결·모임 일정·배정 정책·권한·가이드 템플릿·이관 상태 | 찬양팀 운영 책임자·통합관리자 |

‘가이드’는 이번 주 화면에서 열고, ‘과거 기록’은 출결·등단의 기간 선택으로 연다. 첫 단계부터 별도 대시보드·현황·기록 탭을 중복해서 만들지 않는다.

### 역할별 첫 화면

**조 담당 스탭:** 선택한 모임과 내 조 명단이 먼저 보인다. 미입력 학생만 보기, 이름 검색, 출결 입력이 한 화면에서 끝난다. 운영자가 조나 계정을 아직 연결하지 않았다면 ‘담당 조 배정 대기’와 연락할 담당 역할을 안내한다.

**찬양팀 운영자:** ‘조 편성 미확정 → 출결 미입력 → 등단 미확정’ 순으로 해결할 일을 보여준다. 숫자는 원장에서 계산한 값만 쓰고, 미입력은 결석으로 집계하지 않는다.

**일반 찬양팀 스탭:** 이번 모임 가이드와 확정 등단표를 조회한다. 본인 참석 가능 여부를 받기로 결정하면 자기 항목만 입력한다. 출결·편성·확정 권한은 자동으로 주지 않는다. 학생 개인 로그인과 셀프 출결은 1차 범위에 넣지 않는다.

### 기존 Linear 계열 관리자 화면과의 연결

현재 통합사이트의 서체·녹색 강조색·얇은 구분선·차분한 선택 상태를 이어간다. 장식용 카드보다 검색·필터·명단·작업 상태가 먼저 읽히게 한다. 기존 마이페이지 CSS는 시각 기준으로 참고하되 모달 레이아웃 전체를 그대로 복사하지 않는다. [현재 마이페이지 토큰과 구조](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/app/my-page-workspace.css#L1).

PC에서는 왼쪽 목록과 오른쪽 상세 패널로 학생 정보·등단 배치를 수정한다. 모바일 출결은 가로로 긴 학기 표보다 선택 날짜의 학생 목록을 기본으로 한다. 등단은 모바일에서 1·2부를 전환해 읽고, 편집 권한이 있으면 버튼·선택 메뉴로도 이동할 수 있게 한다. 기존 PC/모바일 보기 선택을 존중한다.

검색·선택 날짜·조는 상세 패널을 닫아도 유지한다. 저장 중·저장 완료·실패·충돌을 구분하고, 실패한 값을 완료된 것처럼 표시하지 않는다. 키보드 조작, 포커스 복귀, ESC, 색 외의 상태 표시는 출시 조건이다.

## 5. 출석은 먼저 의미를 맞춘다

최근 ‘본인이 체크하지 않았는데 출석으로 보인다’는 문의가 있었으므로, **등단 후보 선정이나 확정이 출석을 자동 생성하는 일은 없어야 한다.** 각 기록에서 대상 행사·입력 계정·입력 시각을 확인할 수 있어야 한다. 계정 기록으로 실제 기기를 조작한 사람까지 단정하지 않는다.

| 기록 종류 | 통합 정책 |
|---|---|
| 학생 출석부의 주일 출석 | 기존 attendance/{year}의 O/X 유지. 토요 참석이나 등단 여부로 자동 변경하지 않음 |
| 통합사이트 학기의 사역팀 출석 | 기존 team 출석을 유지. 찬양팀 토요모임과 같은 행사이면 그 기록 하나를 두 화면에서 사용 |
| 학기 훈련 출석 | 기존 training 출석 유지. 사역팀 출석으로 대신 채우지 않음 |
| 별도의 찬양 연습·임시 모임 | 기존 학기 회차와 다른 행사임을 확인한 경우에만 별도 출결 |
| 주일 등단 배정 | 예정·확정된 역할과 위치. 실제 주일 출석 증빙으로 사용하지 않음 |

근거: [DB 소유권과 학생 출석](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/DB_OWNERSHIP.md#L20), [학기 출석 두 범위](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/DB_OWNERSHIP.md#L122), [현재 출석 경로](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/features/semester/paths.ts#L25).

**동일 행사 판정**은 semesterId·실제 teamId·sessionId·모임의 목적·날짜를 대조한 연결표로 한다. 팀 이름이나 같은 날짜만 보고 묶지 않는다. 다일 행사·휴강·임시 모임도 별도 검토한다. 주일 예배 날짜는 명시 필드로 두고 ‘모임 다음날’로 고정하지 않는다.

동일 행사로 연결된 출결은 기존 학기 원장을 단일 저장 원천으로 재사용하는 안부터 검토한다. 단, 아래의 원본 읽기 보호 기준과 양립하는지 먼저 확인해야 한다. 재사용이 가능하면 학기 출석 화면과 찬양팀 화면이 같은 저장 함수를 사용하게 하고, 기존 함수에 필요한 권한·revision 검사를 보강한다. 외부 기록과 기존 기록이 다르면 자동 덮어쓰기하지 않고 대조 목록에 남긴다. 서로 다른 두 출석을 복사해 동기화하는 방식은 피한다.

현행 학생 앱은 두 상태지만 통합 학기와 외부 찬양팀에는 지각이 남아 있다. **신규 찬양팀 UI도 출석·결석 두 상태로 맞추는 방향을 제안**하되, 외부의 과거 지각을 출석으로 바꿀지와 등단 자격 판정에 미치는 영향은 이관 전 확정해야 한다. 과거 원본값은 보존하고 변환 정책·건수를 남긴다. 이번 기획으로 데이터 변환을 실행하거나 승인받은 것으로 보지 않는다. 미입력은 두 상태와 별도로 유지한다.

## 6. 데이터와 권한 설계

### 인물·학기 연결

| 외부 데이터 | 통합 연결 | 보존할 내용 |
|---|---|---|
| terms / meetings | 기존 학기 + 명시적인 회차 연결 | 외부 ID, 원래 날짜·휴강·순서, 연결 여부 |
| students / term_students | 기존 personId를 우선하고 연도별 studentId·학기 appKey에 명시 대응 | 싱어/세션, 부서, 인도 가능 여부, 활동 여부 등 찬양 전용 속성 |
| staff / profiles | 기존 스탭 원장과 Firebase UID를 각각 연결 | 실무 스탭 키와 계정 UID를 구분. 외부 계정 ID는 이관 근거 |
| grouping_versions / group members | 찬양팀 조 편성 버전 | 기존 확정본·담당자·조 구성, 적용 시점 |
| attendance | 동일 행사면 학기 team 출석, 별도 모임이면 찬양 출석 | 원본 상태·작성 정보·revision·대조 결과 |
| stage plans / versions / assignments | 찬양팀 예배별 등단 버전 | 인도자·싱어·콰이어·위치·수동 예외·확정 정보, 주차별 스탭 참석·역할, 후보·제외, 설정 스냅샷·경고·예외 승인 |
| audit events / import files | 접근 제한된 이관 기록·원본 저장소 | 실제 과거 출처·작성 시각, 원본 파일·검증 영수증 |

이름이 같은 학생을 자동 병합하지 않는다. personId가 없으면 원장·학기·기존 ID를 함께 대조하고 미연결 항목은 검토 대기로 둔다. 현재 명단에 없는 과거 학생도 이력에서 누락시키지 않는다. 역사 자료용 외부 참조로 보존하고, 학생 원장 신규 등록은 기존 소유 앱의 정식 흐름으로 처리한다.

찬양팀이 학생 앱의 classes·teacherStaff를 직접 고치지 않는다. 기본 인물 정보 수정은 원장 관리 화면으로 연결하고, 찬양팀 화면에서는 찬양 업무 속성을 수정한다. 학기 신청·훈련 조건을 이관 편의를 위해 우회하지 않는다. 현행 규칙은 일반 학생의 훈련 신청을 요구하며, 고3 2학기와 스탭에 예외를 둔다. [신청 규칙](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/features/semester/intakeRule.ts#L3).

### 전용 데이터 경계 — 아래 경로는 구현 제안

기존 semesters에는 기본 학기·팀·신청·공통 회차 출석을 유지한다. 새 조 편성·등단·가이드·정책 등은 praiseOps/{workspaceId} 같은 별도 업무 경로에 둔다. workspace에는 semesterId와 실제 teamId를 명시한다. 인물 원장을 하나 더 만드는 경로가 아니라 기존 인물의 찬양 업무 연결이다.

관계 조건의 사유, 민감한 제외 사유, 원본 시트, 계정 대응표는 일반 운영 데이터와 분리한다. 접근 범위가 다른 데이터는 통째로 구독하지 않고, 읽기 권한에 맞는 경로에서 가져온다. 필요하다면 praisePrivate와 praiseAccess를 분리하되 실제 스키마·Rules 계약 검증에서 이름과 깊이를 확정한다.

현재 semesters는 여러 역할이 전체를 읽고 관리자 버킷이 쓸 수 있다. 하위 Rules만 추가해서 기존 상위 허용을 취소할 수 없다. 따라서 ‘담당 조만 화면에 표시’와 ‘DB에서도 담당 조만 읽을 수 있음’을 같은 보장으로 설명하면 안 된다. 기존 학기 출석을 재사용하면 신규 찬양팀 쓰기는 담당 범위로 제한할 수 있어도, 기존에 허용된 읽기는 그대로 남는다. 따라서 출석 저장 위치는 아래 원본 보호 기준을 확인한 뒤 확정해야 한다. [현행 Rules](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/attendance-app/database.rules.json#L379), [Firebase 상위 권한 적용 원칙](https://firebase.google.com/docs/database/security/core-syntax#read_and_write_rules_cascade).

### 제안 권한표

외부 v2는 출결 원본의 직접 읽기도 담당 조로 제한한다. 기존 Firebase 학기 원장에 이관하면 원본보다 읽기 범위가 넓어질 수 있으므로 이를 단순한 저장 위치 변경으로 처리하지 않는다. **원본 보호 범위 유지를 기본으로 하고, 운영 데이터 이관 전에 읽기 범위를 확정한다.** 보호 범위가 양립하지 않으면 찬양 출결을 별도 경로의 단일 원천으로 두고 학기 화면도 그 원천을 참조하도록 연결한다. 이 경우 기존 학기 화면의 읽기·쓰기·집계와 옛 저장 경로 차단까지 함께 검증해야 한다.

| 업무 | 통합관리자 | 찬양팀 운영 책임자 | 조 담당 스탭 | 일반 스탭 |
|---|---|---|---|---|
| 팀원 연결·정책·일정 | 관리 | 찬양팀 범위 관리 | 조회 | 필요한 안내 조회 |
| 조 편성·담당 배정 | 관리 | 관리 | 담당 조 조회 | 필요 범위 조회 |
| 토요 출결 입력 | 전체 | 전체 | 담당 조 | 불가 |
| 등단 초안 생성·수정 | 가능 | 가능 | 별도 위임 시 가능 | 불가 |
| 등단 확정·재확정 | 가능 | 가능 | 별도 위임 시 가능 | 불가 |
| 확정 등단표·가이드 | 조회 | 조회 | 조회 | 조회 |
| 원본 시트·민감 사유 | 필요 범위 | 명시 허용 범위 | 불가 | 불가 |
| 전체 사이트 활동 로그 | 기존 통합관리자 권한 | 찬양 업무 이력만 | 허용된 업무 기록만 | 본인 관련 정보만 |

이 표는 **제안하는 업무 권한**이며 현재 구현 상태가 아니다. 기존 목회자·리더의 관리 능력은 accessPolicy의 두 축 계약과 함께 대조한다. 찬양팀 세부 역할을 추가하더라도 전역 SemesterRole을 무조건 늘리거나 retreatAdmins로 승격하지 않는다. 전역 역할과 찬양팀 내부 담당 범위를 결합한 능력 함수로 판단하고, 서버/Rules에서도 검증한다.

외부 v2의 GROUP_STAFF는 전체 등단 생성·수정·확정 도구를 사용할 수 있다. 조 담당자 모두에게 확정 권한을 줄 필요가 있는지 다시 정하는 편이 좋다. [외부 운영 권한 진입점](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/src/lib/api.ts), [외부 권한 설명](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/docs/architecture.md#L48).

## 7. 저장·등단·활동 로그의 필수 계약

**통합 후 새로 만드는 확정본은 운영 당시의 스냅샷으로 보존한다.** 학생의 반·이름·활동 여부가 바뀌어도 과거 등단표를 다시 계산해 바꾸지 않는다. 과거 기록 조회는 해당 예배의 최신 확정 버전을 기본으로 보여주고, 이전 확정본도 이력에서 확인한다.

외부 v2는 등단 인물 ID에 현재 이름을 연결해 표시하는 부분이 있다. 이관 시 원본에 남은 과거 값은 보존하되, 당시 이름이 저장되어 있지 않다면 이를 복원했다고 주장하지 않는다. 그 경우 ‘이관 시점 명단 기준’임을 표시하고 원본의 인물 참조를 함께 남긴다. [원본 등단 인물 저장](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/supabase/migrations/202609040005_stage.sql#L175), [기록 조회 시 이름 연결](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/src/app/admin/terms/%5BtermId%5D/stage-history/page.tsx#L25).

조 편성은 ‘초안 → 수정 → 현재 내용 저장 및 확정’으로 진행한다. 확정 조를 바꿔도 과거 모임의 조 구성은 지우지 않는다. 과거 출결 수정은 운영자 또는 당시 담당자로 범위를 정하고, 현재 담당자가 예전 조 전체를 무조건 수정하게 하지 않는다.

등단 생성 시 사용한 출결·인물·정책·조 편성의 버전을 저장한다. 검토 중 출결이나 정책이 바뀌면 ‘기준 정보 변경’ 표시 후 재검토해야 한다. 중복 클릭·네트워크 재시도는 같은 작업 ID로 한 번만 반영하고, 오래된 revision의 저장은 최신 기록을 덮어쓰지 않는다.

원본 등단 알고리즘은 최근 확정 등단 이력, 목표 인원, 미등단·연속 등단, 학생 후보 중 등단 비율, 스탭 지원, 성별 구성을 고려한다. 그러나 모든 조건이 절대 제한은 아니다. 목표 인원을 우선해 3주 연속 등단이 생기면 경고하는 코드도 있다. **필수 조건과 권장 조건을 설정에서 구분**하고, 예외 확정에는 검토 사실을 남긴다. 특정 실명으로 기본 역할을 정하는 코드는 인물 ID 기반 설정으로 바꾼다. [등단 순위·경고](https://github.com/andew423-source/high-school-worship-team/blob/982dc53ab3ee6d1261736167e5a000deec07974b/worship-admin-v2/src/domain/stage.ts#L224).

출결 화면에는 저장된 계정·시각·변경 이력을 제공한다. 통합관리자 마이페이지의 기존 활동 로그에는 찬양팀 출결 변경·조 확정·등단 확정·권한 변경을 연결한다. 민감한 사유나 연락처 원문은 로그 요약에 복제하지 않는다. 외부 과거 로그는 ‘외부 사이트에서 이관된 기록’으로 표시하고, 이관 작업자를 과거 실제 작성자로 바꾸지 않는다.

현재 활동 로그의 일반 update는 업무와 로그를 같은 원자 쓰기에 묶지만, transaction 도우미는 업무 완료 뒤 별도 로그를 저장한다. 따라서 조·등단 확정에 그 도우미를 붙였다는 이유만으로 업무와 감사 기록의 완전한 동시 저장을 보장하면 안 된다. **버전 검증·업무 변경·로그 원자 저장을 보장하는 방식**을 먼저 검증하거나, 분리 저장이 필요한 경우 누락 감지·재시도·부분 성공을 명시하는 복구 계약을 마련해야 한다. [현재 저장 도우미](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/features/activityLog/write.ts#L60), [transaction 처리](https://github.com/k10k10k10-git/woori-high-apps/blob/4124dedbe1dcd8b4b34c3e3d305bce2d64160446/highschool-app/src/features/activityLog/write.ts#L95).

새 찬양 경로가 기존 로그 분류에 자동 포함되지는 않는다. activityLog의 경로 분류·허용 필드·링크·영역 enum과 Rules를 함께 확장해야 한다. ## 9. 실제 기록을 보존하는 도입 순서

### 0단계 — 원천 확인과 이관 검증

기존 운영은 유지한다. 실제 쓰이는 앱이 v2인지, 이전 D1/R2에만 남은 기록도 있는지 확인한다. Supabase DB·Storage 및 필요 시 legacy 원본을 스냅샷으로 확보하고 복원 가능한지 확인한다. DB 접속 정보나 스냅샷 원문은 저장소·기획 문서에 넣지 않는다.

학생·스탭·계정·학기·회차 ID 대응표와 미연결·충돌 목록을 만든다. 이번 주뿐 아니라 과거 확정 등단표·출결·원본 업로드, 주차별 스탭 참석·역할, 후보·제외 조건, 설정 스냅샷·경고·예외 승인도 이관 범위로 잡는다. 예전 앱과 v2의 중복 기록을 두 번 합산하지 않도록 실제 원천을 확정한다.

동시에 격리된 테스트 환경에서 ‘출결 충돌’, ‘편성 확정과 로그’, ‘담당 조 권한’을 검증한다. **종료 조건:** 복원 가능, 데이터 대응 가능, 핵심 저장 계약 통과. 통과 전에는 운영 입력 창구를 전환하지 않는다.

### 1단계 — 통합 화면과 읽기 전용 이관본

기존 찬양팀 메뉴에 이번 주·팀원 검색·과거 기록 조회를 구현한다. 사전 스냅샷에서 가져온 기록을 기존 앱과 대조한다. 이 기간 실제 출결과 확정은 기존 사이트 한 곳에서만 입력한다. 이관본에는 기준 시점을 표시해 최신 운영 기록처럼 오해하지 않게 한다.

**종료 조건:** 인원·출결 상태별 건수·확정 버전·1/2부 배치·파일 참조가 원본과 일치하고, 미연결 항목이 모두 설명되어야 한다. 실제 운영자와 조 담당자 계정으로 접근 범위를 확인한다.

### 2단계 — 기존 업무를 대체할 수 있는 기능 완성

출결 → 조 편성 → 등단 생성·편집·확정(스탭만 등단 모드 포함) → 이력·내보내기 순으로 완성한다. 개발 단계는 나누되 **기존 사이트를 대체하는 시점에는 현재 쓰는 핵심 기능이 모두 준비되어 있어야 한다.** 부분 완성 때문에 같은 주의 업무를 두 사이트에서 나눠 입력하게 하지 않는다.

원본의 재현 가능한 입력을 사용해 배정 결과·필수 조건·권장 경고를 대조한다. 이미 확정된 과거 등단표는 새 알고리즘으로 다시 생성하지 않고 그대로 보존한다. 변경된 정책은 새 버전으로 표시한다.

### 3단계 — 최종 대조 후 한 곳으로 전환

실제 모임·예배 시간대를 피한 전환 시간을 정한다. 화면·웹 API뿐 아니라 기존 세션의 Supabase 직접 테이블 쓰기와 RPC까지 동결됐는지 검증한 뒤 최종 스냅샷·변경분을 확보한다. legacy가 운영 중이면 실제 D1 쓰기 진입점도 포함한다. 이관은 결정적 외부 ID와 작업 ID로 재실행해도 중복이 생기지 않게 한다. 건수·참조·출결·확정본을 다시 대조한 뒤 통합사이트 입력을 연다.

전환 후 기존 사이트의 쓰기 API도 차단해 오래된 북마크로 수정되지 않게 한다. 기존 URL에서는 새 주소를 안내하고 필요한 과거 기록은 읽기 전용으로 보존한다. 사용자에게 알릴 내용은 새 접속 위치·로그인 방법·담당 조·저장 확인 방법으로 간단히 정리한다.

실제 운영 데이터 적재·변환, 계정·권한 변경, Rules 배포는 이 기획만으로 실행하지 않는다. 구현 단계에서 대상 경로·건수·백업·검증 결과를 준비한 뒤 해당 작업의 명시 승인 범위를 확인한다. 이 문서 작성 단계에는 그 승인이나 운영 변경이 필요하지 않다.

**복구:** 전환 전에 실패하면 기존 앱을 계속 사용한다. 전환 후 새 기록이 생겼다면 우선 입력을 잠그고 그 변경분을 내보낸다. 이를 보존·재반영하는 검증 없이 예전 앱만 다시 열거나 이전 스냅샷으로 덮어쓰지 않는다. 데이터 복구와 UI 버전 복귀를 별도 절차로 둔다.

### 4단계 — 운영 확인 후 확장

첫 모임 가이드를 회차별 편집·게시로 확장하고 나눔마블 PPTX·보드·진행문을 자료실에 연결한다. 게임 규칙을 통일하고 날짜·실명 면접표는 공개 다운로드에 포함되지 않게 검토한다. 콘티·악보·연습자료는 실제 필요를 확인한 다음 별도 기능으로 설계한다. 온라인 보드게임 구현은 이번 통합의 필수 범위가 아니다.

자동 조 편성과 PDF/이미지 내보내기는 필요한 화면에서만 로딩한다. 현재 주·선택 조 중심으로 구독하고 과거 기록은 페이지 단위로 조회한다. 큰 명단을 수천 번 탐색하는 조 편성은 화면을 멈추지 않도록 실행 위치와 취소·진행 표시를 정한다. 성능 목표는 개발 시 실제 지원 기기·명단 크기로 측정해 정하며, 이번 검토로 속도 개선 수치를 주장하지 않는다.

출시 전 최소 확인 사항은 다음과 같다.

- 원본 백업 복원, 이관 전후 상태별 건수·확정 버전·참조 무결성, 같은 이관 재실행 시 중복 0건.
- 다른 조·권한 없는 계정·휴강 회차 직접 쓰기 거절. 기존 자기 역할 조회와 두 앱의 권한 계약 유지.
- 두 기기의 같은 셀 수정 충돌, 미저장 조 편성 확정, 중복 확정, 기준 출결 변경 후 등단 확정 시나리오.
- 등단 확정·페이지 열기·로그인으로 주일 학생 출석이 생성되지 않음. 출결을 지우면 미입력으로 돌아옴.
- 과거 확정본이 현재 명단 변경에도 보존됨. PNG/PDF의 날짜·1/2부·인도자·배치가 확정본과 일치.
- 모바일 출결, PC 편성, 검색 후 상세 수정·복귀, 키보드 편집, 빈 상태·실패·충돌 화면.
- 대상 앱의 lint → typecheck → test → build. 공유 Rules 계약은 두 앱 검사와 emulator 검증. 인증 E2E는 실제 유효한 테스트 인증으로 수행하고 미실행이면 별도 표시.
- 운영 반영 시 PR 검토·병합, Rules 백업·대조·승인된 배포, Vercel Ready와 /api/version 커밋 대조. 학생 앱 코드가 바뀌지 않으면 학생 Hosting을 불필요하게 다시 배포하지 않음.

이번에는 문서·근거 링크를 검사했으며 위 출시 검사를 실행한 것은 아니다.

구현 범위는 ‘찬양팀 주간 운영 + 기존 기록 보존’에 집중하는 것이 좋다. **첫 화면은 이번 주 할 일, 데이터는 명시 연결, 출결은 한 원장, 등단은 확정 이력 보존**을 기준으로 삼으면 현재 통합사이트와 자연스럽게 이어진다.
