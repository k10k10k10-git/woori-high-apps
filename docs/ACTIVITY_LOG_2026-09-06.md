## 저장과 증거 범위

통합 앱의 기존 업무 DB 모듈은 `src/features/activityLog/write.ts`를 통한다. 일반 set/update/remove는 기존 원장 patch와 `activityLogs/events/{eventId}` 한 건을 같은 루트 update로 저장한다. 원장 쓰기가 거부되면 로그도 저장되지 않고, 로그 검증이 거부되면 원장 쓰기도 취소된다. 전체 명단을 교체해도 저장 호출당 로그 한 건이므로 Firebase 함수의 이벤트 수 제한을 추가하지 않는다.

Rules는 `actor.uid === auth.uid`, 선택 이름은 `auth.token.name`과 일치, 두 시각은 서버 `now`와 일치, 기존 로그 수정·삭제 금지를 검증한다. 통합관리자(`admins/{uid} === true`)만 읽는다. 기존 승인 계정은 자기 계정 기록을 새로 추가하며, 미승인 계정은 본인 접근/사이트 요청 경로의 로그만 추가할 수 있다. 로그 권한이 기존 원장 쓰기 권한을 대신하지 않는다.

이것은 **최신 앱의 저장 활동 로그**다. 다음 제한을 숨기지 않는다.

- 로그의 대상·업무 설명은 클라이언트가 제출한 정보다. Rules가 인증 계정과 시각을 검증하지만 모든 DB 변경을 독립 관찰하거나 사람이 직접 클릭했음을 증명하지 않는다.
- 과거 기록은 소급 생성하지 않는다. 구버전 브라우저·콘솔·직접 DB 쓰기는 누락될 수 있다.
- 사전 DB 조회로 이전 값을 추측하지 않는다. 신규/기존 여부를 별도로 확인하지 않는 set/update는 **저장**으로 표시하며, 출석의 `before`는 **기록하지 않음**, `after`는 **저장값**이다.
- 이가드 인원체크와 현장 접수의 트랜잭션은 기존 노드 범위를 유지하고 확정 후 이력을 별도로 추가한다. 그 사이 브라우저 종료·통신 실패에는 로그가 빠질 수 있다. 로그만 실패하면 `ActivityLogAfterCommitError`로 업무는 저장됐음을 알리고 재시도로 토글하지 않게 한다. 중단/무변경 트랜잭션에는 로그를 남기지 않는다.
- 백업 전용 쓰기와 알림 확인은 로그 잡음에서 제외한다. 여러 대상을 바꾸는 호출은 한 건으로 묶고 최대 30개 대상/필드와 생략 개수를 표시한다. 자동 이력 삭제는 넣지 않았다.

## 설계 검토 근거

원장 leaf별 Cloud Functions 수집도 검토했으나 적용하지 않았다. RTDB 한 번의 쓰기가 파생시키는 함수 수/이벤트 크기 제한 때문에 기존 학기 전체 삭제나 공개·비공개 명단 원자 교체가 실패할 수 있었다. 예컨대 참가자 501명의 공개/연락처 교체는 1,002개 leaf 이벤트를 만든다. 이 제한을 끄거나 원자 저장을 임의로 나누는 대신 앱 저장 단위의 로그를 선택했다. [Firebase RTDB 제한](https://firebase.google.com/docs/database/usage/limits)

Rules의 `now`, `auth`, 추가 전용 검증 및 문자열 연산은 [Firebase Security Rules 공식 참조](https://firebase.google.com/docs/reference/security/database)를 기준으로 에뮬레이터에서 확인했다. RTDB Rules에는 `numChildren()`이 없으므로 변화 목록은 0~29 인덱스만 허용해 크기를 제한한다.
