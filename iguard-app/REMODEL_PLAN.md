근거: 2026 여름수련회 스탭 피드백 6건 + 실제 사용 큐싯 시트 12개 탭 전수 해부

## 0. 이 문서를 읽는 사람에게

이 문서는 **코드를 바꾸지 않는다.** 무엇을 왜 바꿔야 하는지와 그 순서를 정한다.
실행자는 이 문서만 보고 완주할 수 있어야 하며, ⚠ 표시된 항목은 **사용자 승인 없이 진행하지 않는다.**

작업 전 반드시 함께 읽을 것: 루트 `CLAUDE.md`(안전 4문답·실수 목록) → `iguard-app/CLAUDE.md`(패턴 1~27) → `DB_OWNERSHIP.md`.

## 1. 목표와 성공 기준

**최종 목표**: 이가드 사역에서 구글 스프레드시트를 사용하지 않는다. 큐싯 제작·수정·현장 반영이 전부 사이트 안에서 일어난다.

성공 기준은 "기능이 있다"가 아니라 **측정 가능한 이탈 감소**로 둔다:

| # | 기준 | 측정 방법 |
|---|---|---|
| S1 | 큐싯 시트 12개 탭 중 **앱이 대체하지 못하는 탭이 0개** | 아래 2장 대응표로 확인 |
| S2 | 여름수련회 큐싯 **214건 동선 배정 전부**가 앱 데이터로 손실 없이 표현됨 | 마이그레이션 검증 스크립트 건수 대조 |
| S3 | 현장에서 큐싯이 바뀔 때 **시트를 열지 않고** 앱에서 고칠 수 있다 | 리허설 QA 시나리오 |
| S4 | 다음 설문에서 "카톡으로 물어본 이유"에 **"큐싯 변경"이 사라진다** | 2027 겨울 설문 |

**비목표(하지 않을 것)**: 스프레드시트보다 타이핑이 편한 에디터를 만드는 것. 자유 입력·복붙·Ctrl+Z에서 시트를 이길 수 없고, 이길 필요도 없다. 앱이 이기는 지점은 **왕복이 사라지는 것** 하나다 — 고치는 즉시 동선·개인 큐카드·검증·인원체크에 반영된다.

## 3. 핵심 문제 — 현재 데이터 모델이 시트를 담지 못한다

### 3.1 갭 A: 블록 안의 "구간(phase)" 개념이 없다 ⚠ 최우선

현재 모델은 `IguardMovement.id = ${staffId}__${blockId}` — **한 스탭은 한 블록에 한 포스트**다.

실제 시트는 한 블록 안에 여러 구간이 있고, 구간마다 배정이 다르다:

```
저녁 식사 17:40~19:30
  * 강당 → 식당    - 밥절: 이채희sf [후밥]
  * 식당 → 숙소    - 1층 퇴식구: 전예성sf, 박혜원sf [선밥]
                   - 숙소 층장: 박성준sf(1층), 도윤성sf(2층+별관), 이주하sf(3층) [선밥]
  * 숙소 → 강당    - 숙소 층장: 송진혁sf(1층), 이채희sf(2층+별관), 전예성sf(3층)
```

**실측**: 시간 블록 22개(1일차 9 / 2일차 9 / 3일차 4), 동선 배정 214건, 구간 헤더 24종.
**22개 블록 중 7개(32%)에서 같은 스탭이 한 블록에 2개 이상 포스트를 맡는다.**

이 갭이 만든 실제 피해 — 피드백 B: *"교대가 있는지는 써있지 않아서(ex 층장교대)"*.
위 예시에서 숙소 층장은 `식당→숙소` 구간(박성준·도윤성·이주하)과 `숙소→강당` 구간(송진혁·이채희·전예성)에서 **사람이 바뀐다.** 앱은 블록당 1포스트만 저장하므로 교대가 원천적으로 표현 불가능하고, 스탭은 카톡으로 물어볼 수밖에 없었다.

### 3.2 갭 B: "미정 배정"이 없다

시트에는 포스트·구간·선밥후밥이 확정됐는데 사람만 비어 있는 슬롯이 정식으로 존재한다(실측 5건):

```
3일차 점심식사
  - 강당 로비: sf [후밥]     ← 포스트 확정, 담당 미정
  - 1층 퇴식구: sf [선밥]
```

피드백 C: *"셋째날은 빈칸으로 가져가고 이런 수련회이면…"* — 변동이 잦은 수련회의 정상 운영 방식이다.
현재 앱은 이 개념이 없어 임포트해도 동선이 0건 생성되고, 검증 화면은 "미배정"과 "아직 안 정한 자리"를 구분하지 못한다.

### 3.3 갭 C: 셀 서식이 데이터다

기타 칸 스탭 명단에 명시: **볼드=선발대 · 밑줄=조스탭 불가 · 파란색=후발**.
CSV 임포트로는 가져올 수 없다. `선발대/후발`은 행정 `teachers.corps`로 이미 관리되지만 **"조스탭 불가"는 앱에 없다.**

### 3.4 갭 D: 부수 표기들

| 표기 | 예 | 현재 처리 |
|---|---|---|
| 괄호 상세 | `박성준sf(1층)`, `주예원sf(A동 1,2층)` | 버려짐 |
| 건물군 분기 | `*(위) 숙소 → 강당`, `*(아래) 식당 → 숙소` | 구간 개념이 없어 버려짐 |
| 비스탭 주체 | `물 배부: 행정팀`, `방 뒷정리: 이가드sf` | 이름 매칭 실패로 버려짐 |
| 작업 메모 | `둘날부터 김동연 동선 넣어야함` | `notice`에 뭉뚱그려 들어감 |
| 선밥/후밥 | `[선밥]` 21건 / `[후밥]` 14건 | `IguardMovement.round` 존재 — **그대로 사용 가능** |

## 4. 새 데이터 모델

### 4.1 신규: `IguardSegment` (구간)

블록과 동선 사이에 한 계층을 넣는다.

```ts
/** 시간 블록 안의 이동 구간. 시트의 "* 강당 -> 식당" 한 줄에 대응한다. */
export interface IguardSegment {
  id: string;              // push id
  blockId: string;
  order: number;           // 블록 안 표시 순서 (0부터)
  label: string;           // "강당 → 식당" (표시 원문)
  zone?: "위" | "아래" | null;  // 시트의 *(위) / *(아래) 건물군 분기
  note?: string | null;
  source?: "sheet" | "manual";
}
```

경로: `retreats/{retreatId}/iguard/segments/{segmentId}` — **이가드 소유 노드, 소유권 변경 없음.**

블록에 구간이 하나도 없어도 된다(구간 없는 블록 = 단순 블록). 구간이 없는 블록의 동선은 아래 **기본 구간**에 붙는다.

### 4.2 변경: `IguardMovement`

```ts
export interface IguardMovement {
  id: string;              // ${segmentId}__${postId}__${staffId ?? `tbd${slot}`}
  segmentId: string;
  blockId: string;         // 비정규화 — 블록 단위 조회·마이그레이션 호환용
  postId: string;
  staffId?: string | null; // null = 미정 배정 (갭 B)
  slot?: number;           // 미정 슬롯 구분 (staffId가 null일 때만 사용)
  round?: "선밥" | "후밥";
  detail?: string | null;  // 괄호 상세 — "1층", "A동 1,2층" (갭 D)
  actor?: string | null;   // 스탭이 아닌 주체 — "행정팀", "이가드sf" (갭 D)
  note?: string;
  source?: "sheet" | "manual";
}
```

**키 설계 근거**: 자연키 `(segmentId, postId, staffId)`는 유일하다 — 같은 사람이 같은 구간의 같은 포스트에 두 번 배정되는 일은 의미가 없다. 복합키를 유지하면 `movementReconcile.ts`의 재임포트 로직(패턴 18)이 지금 구조 그대로 동작한다. push id로 바꾸면 reconcile이 매번 자연키 맵을 새로 만들어야 해 변경 폭이 커진다.

⚠ 키 구성요소는 전부 안전 문자다(push id·행정 teacher id). 한글 이름은 키에 넣지 않는다.

### 4.3 신규: GBS 장소

```ts
/** 조별 GBS 장소. 시트 "GBS 장소" 탭 대체. */
export interface IguardGbsPlace {
  groupId: string;
  place: string;           // "숙소동 분임실 131호"
  updatedAt?: number;
}
```

경로: `retreats/{retreatId}/iguard/gbs/{groupId}` — **이가드 소유.**

시트 오른쪽의 "장소 → 조 목록"(대강당: 7조, 10조, 15조)은 **역방향 뷰**이므로 저장하지 않고 화면에서 파생한다.

연계 이득: 동선 구간에 `강당 → GBS장소`가 실재하므로, 개인 큐카드와 조별 정보에서 **"우리 조 GBS 장소"** 를 바로 보여줄 수 있다.

### 4.4 전체 개요 격자 — **새 데이터 없음**

시트의 개요 탭(행=시간, 열=일차)은 `schedule`의 `day`·`start`·`end`·`label`만으로 100% 파생된다.
**새 DB 경로 0개, 새 뷰 1개**만 만든다. 시간 축은 반드시 `scheduleTime.ts`의 헬퍼를 쓴다 — 시트에 `25:00`·`26:00` 행이 실재하므로 24시+ 표기(패턴 11)를 그대로 태워야 한다.

### 4.5 `paths.ts` 추가 항목

```
iguardSegments(retreatId)          → retreats/{id}/iguard/segments
iguardSegment(retreatId, segId)    → retreats/{id}/iguard/segments/{segId}
iguardGbs(retreatId)               → retreats/{id}/iguard/gbs
iguardGbsGroup(retreatId, groupId) → retreats/{id}/iguard/gbs/{groupId}
```

`DB_OWNERSHIP.md`와 `iguard-app/CLAUDE.md`의 소유권 표에 두 노드를 **이가드 소유(읽기+쓰기)** 로 추가한다. 행정 앱은 이 노드를 읽지 않는다 → **두 앱이 함께 읽는 노드가 아니므로 형태 변경 에스컬레이션(루트 CLAUDE.md #3) 대상이 아니다.**

## 5. 마이그레이션 ⚠ 사용자 승인 + 스냅샷 백업 필수

### 5.1 원칙

- **무손실**: 기존 동선 214건이 1건도 사라지지 않는다.
- **되돌릴 수 있음**: 스냅샷 하나로 원상복구된다.
- **전체 덮어쓰기 금지**: 루트 CLAUDE.md 실수 #2. 단일 경로 `update()`의 다중 경로 묶음만 사용하고, `set()`으로 `movements` 노드 전체를 쓰지 않는다.

### 5.2 절차

1. **드라이런(읽기 전용)** — 변환 결과를 파일로만 출력한다. 보고 항목: 대상 수련회 수, 기존 동선 건수, 생성될 기본 구간 수, 변환 후 동선 건수, **불일치 0 확인**.
2. **스냅샷** — `retreats/{id}/iguard/movements`와 `schedule`를 JSON으로 내려 `backups/`에 타임스탬프로 저장. 복구 명령을 함께 기록한다.
3. **실행** — 수련회 1개씩. 각 블록마다 **기본 구간**(`order:0`, `label:"전체"`, `source:"manual"`)을 만들고, 기존 동선 `${staffId}__${blockId}` → `${defaultSegmentId}__${postId}__${staffId}`로 옮긴다. `postId`·`round`·`note`·`source`는 그대로 보존.
4. **검증** — 마이그레이션 후 건수 대조 + 개인 큐카드에서 임의 스탭 3명의 동선이 이전과 동일한지 육안 확인.
5. **롤백 기준** — 건수 불일치가 1건이라도 나오면 즉시 스냅샷 복원.

### 5.3 하위호환

- 구버전 키(`staffId__blockId`) 레코드를 읽는 코드를 **한 시즌 유지**한다. `segmentId`가 없는 동선은 해당 블록의 기본 구간에 속한 것으로 간주한다.
- 이 하위호환은 2027 겨울수련회 종료 후 제거한다.

## 6. 단계별 실행 계획

각 단계는 **1단계 = 1커밋 이상**, 기준 검증(`npx tsc --noEmit` 0 errors + `npm test` 전체 통과 + 필요 시 `npm run build`)을 매 단계 통과해야 한다.

### P1. 동선 모델 확장 (기반)
- `types.ts`에 `IguardSegment` 추가, `IguardMovement` 필드 확장
- `paths.ts`에 segments 경로 추가
- `db.ts`에 `subscribeToIguardSegments`(⚠ `onError` 파라미터 필수 — 패턴 16) + CRUD
- `useRetreatData`에 구독 추가 + `fail("segments")` 배선 (패턴 1)
- 기존 화면은 **기본 구간만 사용**하도록 어댑터를 두어 동작 불변
- 테스트: 기본 구간 어댑터가 구버전 동선을 그대로 읽는지 (하위호환 고정)

### P2. 마이그레이션 ⚠ 승인 후
- 5장 절차 그대로. 드라이런 결과를 사용자에게 보고하고 승인받은 뒤 실행.

### P3. 큐싯 파서 확장 + 전체 개요 격자
- `cueSheet.ts`가 `담당` 칸의 `* 구간` / `- 포스트: 이름sf(상세) [선밥]` 구조를 구간 단위로 파싱
  - ⚠ 파싱 순서 불변식 유지: **시간 유무 → 날짜 판정**(패턴 10). 구간 파싱은 그 뒤에 붙인다.
  - ⚠ `자정 넘김` 정규화(`resolveOvernight`, 패턴 10b)는 블록 단위 그대로 — 구간은 블록 시간을 상속한다.
  - 이름 파싱은 `busStaff.ts`의 `parseBusStaff` 규칙을 재사용한다(패턴 14). 새 파서를 만들지 않는다.
  - `sf`만 있는 슬롯 → `staffId: null` 미정 배정으로 생성 (갭 B)
  - `행정팀`·`이가드sf` → `actor` 필드로 (갭 D)
- `movementReconcile.ts`를 구간 단위로 확장. **수동 배정 보존 규칙(패턴 18)을 그대로 유지**한다.
- 전체 개요 격자 뷰 신규 (`schedule` 파생, 새 DB 경로 없음)
- 테스트: 실제 여름 큐싯 CSV를 픽스처로 넣고 **구간 24종·동선 214건·미정 5건이 정확히 재현되는지** 고정

### P4. GBS 장소
- `IguardGbsPlace` + 경로 + 구독 + 편집 화면
- 조별 정보·개인 큐카드에 "우리 조 GBS 장소" 표시
- 역방향(장소 → 조 목록) 뷰는 파생

### P5. 큐싯 에디터 (본체)
- 스탭 전체 큐싯을 **앱에서 직접 편집**: 블록 추가/삭제/순서, 구간 추가/삭제, 포스트별 담당자 지정(미정 포함)
- 동시 편집 안전성: 단일 경로 `update()`만 사용. 인원체크와 동일한 원칙(패턴 15) — `set`으로 목록 전체를 쓰지 않는다.
- 시트 임포트는 **초기 1회 마이그레이션 도구**로 격하한다(상시 동기화 아님). 격하 시점에 패턴 19의 신선도 배너는 역할이 끝난다.

### P6. 현장 딜레이 대응 (축 4)
- 블록에 `actualStart` 개념 추가 → "지금 여기까지 왔음"을 찍으면 이후 일정이 함께 밀린다
- 개인 큐카드의 고정 카드는 계획 시각이 아니라 **진행 상태** 기준으로 판정
- 피드백 D의 "전·후 일정을 보려는데 현재 일정이 고정돼 있어 어려웠다"를 여기서 해소
- ⚠ 시계 tick으로 사용자 선택을 덮지 않는다(패턴 17)

**P6 이후에도 남는 것**: 갭 C의 "조스탭 불가" 표기. 행정 `teachers`에 필드 추가가 필요해 **행정 앱과 협의 대상**이다. 이가드 단독으로 결정하지 않는다.
