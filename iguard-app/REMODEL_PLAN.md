## 1. 목표와 성공 기준

**최종 목표**: 이가드 사역에서 구글 스프레드시트를 사용하지 않는다. 큐싯 제작·수정·현장 반영이 전부 사이트 안에서 일어난다.

성공 기준은 "기능이 있다"가 아니라 **측정 가능한 이탈 감소**로 둔다:

| # | 기준 | 측정 방법 |
|---|---|---|
| S1 | 큐싯 시트 12개 탭 중 **앱이 대체하지 못하는 탭이 0개** | 아래 2장 대응표로 확인 |
| S2 | 여름수련회 큐싯 **214건 동선 배정 전부**가 앱 데이터로 손실 없이 표현됨 | 마이그레이션 검증 스크립트 건수 대조 |
| S3 | 현장에서 큐싯이 바뀔 때 **시트를 열지 않고** 앱에서 고칠 수 있다 | 리허설 QA 시나리오 |
| S4 | 다음 설문에서 "카톡으로 물어본 이유"에 **"큐싯 변경"이 사라진다** | 2027 겨울 설문 |
| S5 | **큐싯을 만들어본 적 없는 스탭이 설명 없이 초안을 만들 수 있다** | 9장 관찰 테스트 |
| S6 | **수제 명찰카드를 손으로 만들지 않는다** — 앱이 인쇄해준다 | 3.5절 카드 6개 섹션 전부 자동 생성 |

**S5가 이 프로젝트의 진짜 관문이다.** 수련회를 섬기는 사람은 매번 바뀐다. 장소도 동선도 바뀐다. 따라서 "이 앱을 아는 사람이 쓰기 좋은가"가 아니라 **"처음 보는 사람이 쓸 수 있는가"** 로 판정한다.

**비목표(하지 않을 것)**: 스프레드시트보다 타이핑이 편한 에디터를 만드는 것. 자유 입력·복붙·Ctrl+Z에서 시트를 이길 수 없고, 이길 필요도 없다. 앱이 이기는 지점은 **왕복이 사라지는 것** 하나다 — 고치는 즉시 동선·개인 큐카드·검증·인원체크에 반영된다.

## 3. 핵심 문제 — 현재 데이터 모델이 시트를 담지 못한다

### 3.1 갭 A: 블록 안의 "구간(phase)" 개념이 없다 ⚠ 최우선

현재 모델은 `IguardMovement.id = ${staffId}__${blockId}` — **한 스탭은 한 블록에 한 포스트**다.

실제 시트는 한 블록 안에 여러 구간이 있고, 구간마다 배정이 다르다:

```
저녁 식사 17:40~19:30
  * 강당 → 식당    - 밥절: 이채희sf [후밥]
  * 식당 → 숙소    - 1층 퇴식구: 전예성sf, 박혜원sf [선밥]
                   - 숙소 층장: 박성준sf(1층), 도윤성sf(2층+별관), 이주하sf(3층) [선밥]
  * 숙소 → 강당    - 숙소 층장: 송진혁sf(1층), 이채희sf(2층+별관), 전예성sf(3층)
```

**실측**: 시간 블록 22개(1일차 9 / 2일차 9 / 3일차 4), 동선 배정 214건, 구간 헤더 24종.
**22개 블록 중 7개(32%)에서 같은 스탭이 한 블록에 2개 이상 포스트를 맡는다.**

이 갭이 만든 실제 피해 — 피드백 B: *"교대가 있는지는 써있지 않아서(ex 층장교대)"*.
위 예시에서 숙소 층장은 `식당→숙소` 구간(박성준·도윤성·이주하)과 `숙소→강당` 구간(송진혁·이채희·전예성)에서 **사람이 바뀐다.** 앱은 블록당 1포스트만 저장하므로 교대가 원천적으로 표현 불가능하고, 스탭은 카톡으로 물어볼 수밖에 없었다.

### 3.2 갭 B: "미정 배정"이 없다

시트에는 포스트·구간·선밥후밥이 확정됐는데 사람만 비어 있는 슬롯이 정식으로 존재한다(실측 5건):

```
3일차 점심식사
  - 강당 로비: sf [후밥]     ← 포스트 확정, 담당 미정
  - 1층 퇴식구: sf [선밥]
```

피드백 C: *"셋째날은 빈칸으로 가져가고 이런 수련회이면…"* — 변동이 잦은 수련회의 정상 운영 방식이다.
현재 앱은 이 개념이 없어 임포트해도 동선이 0건 생성되고, 검증 화면은 "미배정"과 "아직 안 정한 자리"를 구분하지 못한다.

### 3.3 갭 C: 셀 서식이 데이터다

기타 칸 스탭 명단에 명시: **볼드=선발대 · 밑줄=조스탭 불가 · 파란색=후발**.
CSV 임포트로는 가져올 수 없다. `선발대/후발`은 행정 `teachers.corps`로 이미 관리되지만 **"조스탭 불가"는 앱에 없다.**

### 3.4 갭 D: 부수 표기들

| 표기 | 예 | 현재 처리 |
|---|---|---|
| 괄호 상세 | `박성준sf(1층)`, `주예원sf(A동 1,2층)` | 버려짐 — ⚠ **3.5절에서 이 값이 결정적임이 드러났다** |
| 건물군 분기 | `*(위) 숙소 → 강당`, `*(아래) 식당 → 숙소` | 구간 개념이 없어 버려짐 |
| 비스탭 주체 | `물 배부: 행정팀`, `방 뒷정리: 이가드sf` | 이름 매칭 실패로 버려짐 |
| 작업 메모 | `둘날부터 김동연 동선 넣어야함` | `notice`에 뭉뚱그려 들어감 |
| 선밥/후밥 | `[선밥]` 21건 / `[후밥]` 14건 | `IguardMovement.round` 존재 — **그대로 사용 가능** |

### 3.5 ⭐ 갭 E: 앱의 진짜 경쟁자는 시트가 아니라 **종이 명찰카드**였다

실물 확인: `26 여름 이가드 동선 최종.pdf`(10면). 스탭들이 명찰에 달고 다닌 카드다.

독립 증언 2건:
> *"많이 쓰는 이가드들이 앱이 있어도 **자기 명찰에 달린 카드** 보고 다니니까 그닥 쓸 일이 없었나 싶기도 해"* (행정팀 대화, 2026-07-29)
> *"식사순서와 자리배치는 수련회 현장에서는 사용할 일이 없었음. **완성된 순서를 따로 수제 큐카드로 만들어서 들고다니기 때문**"* (설문 ⑦)

**카드의 실제 구성** (박세원·박혜원 카드 대조):

| 섹션 | 성격 | 앱 보유 여부 |
|---|---|---|
| 첫날 호차 순서 — `1호차(10조,14조,15조) With 장현민, 최지성…` | 개인 | ✅ `buses` |
| 첫날/둘날 식사 이동 순서 — `4조→11조→12조→…` 전체 | 공통 | ✅ `meals` + `mealOrder` |
| GBS 장소 이동 순서 — `숙소 3층: 8조(333호), 14조(331호)` | 공통/개인 | ❌ **GBS 없음** (P4) |
| 집회 이동 순서 — `강당 진행 조 / 중강당 진행 조` | 공통 | ✅ `seating` |
| **본인 담당 구역의 호실 → 학생 이름** — `303호(홍재나) 403호(심사랑)` | 개인 | ⚠ 재료는 있으나 **"담당 구역" 개념이 없음** |
| 특정 조건 학생 명단 — `18:40 수찬 학생들`, `선교 학생` | 개인 | ❌ **학생 속성 없음** |

**여기서 나온 세 가지 결론:**

1. **앱의 개인 큐카드와 종이 카드는 다른 물건이다.**
   앱 = "시간 → 내가 설 포스트(동선)". 종이 = "**내 담당 구역의 명단과 순서**".
   현장에서 스탭이 실제로 손에 들고 다닌 건 후자였다. 설문 ⑦의 *"급할 때는 결국 구글시트 들어가서 보는 경우가 더 많았음"*, *"개인 큐카드 개선이 가장 중요한 개선점"* 이 같은 곳을 가리킨다.

2. **`IguardMovement.detail`(괄호 상세)이 예상보다 훨씬 중요하다.**
   `아래 숙소 층장: 박혜원sf(C동 3,4층)`의 `(C동 3,4층)`이 곧 **담당 구역**이고, 이 값만 있으면 방배정·조편성과 결합해 **"내 담당 구역의 호실별 학생 명단"을 자동 생성할 수 있다.** 4.2절에서 부수 필드로 넣었던 것이 명찰카드 자동 생성의 핵심 키였다.

3. **종이와 싸우지 말고 앱이 종이를 만들어준다.**
   즉시성·배터리·네트워크에서 앱이 종이를 이길 방법은 없다. 대신 지금 **손으로 만드는** 카드를 앱이 자동 생성·인쇄하면:
   (a) 수제 제작 노동이 사라지고, (b) 앱을 안 쓰는 스탭에게도 앱의 산출물이 전달되며, (c) **큐싯이 앱에 있어야 인쇄가 되므로 저작을 앱으로 옮길 동기가 생긴다.**
   `exportUtils.printAsPDF`가 이미 있고, ⚠ 사용자 데이터는 반드시 `escapeHtml()`을 거친다(패턴 13).

### 3.6 갭 F: 조별 정보에 학생 이름이 없다

`RoomsView`는 방을 `방번호: 인원수` 칩으로만 표시하고, 학생 이름이 나오는 것은 당일참석자뿐이다(코드 확인 2026-07-30).

> 행정팀 대화: *"조별 정보에 애들 이름이 없다는 피드백이 있었던"*
> 설문 ⑦: *"인원 확인이나 학생이 물어봐서 숙소를 찾아야 했는데 생각보다 쉽게 찾기가 힘들었음"*

전역 검색(2026-07-30 배포)이 우회로를 만들었지만, 조별 정보 자체의 결손은 그대로다.


## 4. 새 데이터 모델

### 4.1 신규: `IguardSegment` (구간)

블록과 동선 사이에 한 계층을 넣는다.

```ts
/** 시간 블록 안의 이동 구간. 시트의 "* 강당 -> 식당" 한 줄에 대응한다. */
export interface IguardSegment {
  id: string;              // push id
  blockId: string;
  order: number;           // 블록 안 표시 순서 (0부터)
  label: string;           // "강당 → 식당" (표시 원문)
  zone?: "위" | "아래" | null;  // 시트의 *(위) / *(아래) 건물군 분기
  note?: string | null;
  source?: "sheet" | "manual";
}
```

경로: `retreats/{retreatId}/iguard/segments/{segmentId}` — **이가드 소유 노드, 소유권 변경 없음.**

블록에 구간이 하나도 없어도 된다(구간 없는 블록 = 단순 블록). 구간이 없는 블록의 동선은 아래 **기본 구간**에 붙는다.

### 4.2 변경: `IguardMovement`

```ts
export interface IguardMovement {
  id: string;              // ${segmentId}__${postId}__${staffId ?? `tbd${slot}`}
  segmentId: string;
  blockId: string;         // 비정규화 — 블록 단위 조회·마이그레이션 호환용
  postId: string;
  staffId?: string | null; // null = 미정 배정 (갭 B)
  slot?: number;           // 미정 슬롯 구분 (staffId가 null일 때만 사용)
  round?: "선밥" | "후밥";
  detail?: string | null;  // 괄호 상세 — "1층", "A동 1,2층" (갭 D)
  actor?: string | null;   // 스탭이 아닌 주체 — "행정팀", "이가드sf" (갭 D)
  note?: string;
  source?: "sheet" | "manual";
}
```

**키 설계 근거**: 자연키 `(segmentId, postId, staffId)`는 유일하다 — 같은 사람이 같은 구간의 같은 포스트에 두 번 배정되는 일은 의미가 없다. 복합키를 유지하면 `movementReconcile.ts`의 재임포트 로직(패턴 18)이 지금 구조 그대로 동작한다. push id로 바꾸면 reconcile이 매번 자연키 맵을 새로 만들어야 해 변경 폭이 커진다.

⚠ 키 구성요소는 전부 안전 문자다(push id·행정 teacher id). 한글 이름은 키에 넣지 않는다.

### 4.3 신규: GBS 장소

```ts
/** 조별 GBS 장소. 시트 "GBS 장소" 탭 대체. */
export interface IguardGbsPlace {
  groupId: string;
  place: string;           // "숙소동 분임실 131호"
  updatedAt?: number;
}
```

경로: `retreats/{retreatId}/iguard/gbs/{groupId}` — **이가드 소유.**

시트 오른쪽의 "장소 → 조 목록"(대강당: 7조, 10조, 15조)은 **역방향 뷰**이므로 저장하지 않고 화면에서 파생한다.

연계 이득: 동선 구간에 `강당 → GBS장소`가 실재하므로, 개인 큐카드와 조별 정보에서 **"우리 조 GBS 장소"** 를 바로 보여줄 수 있다.

### 4.4 전체 개요 격자 — **새 데이터 없음**

시트의 개요 탭(행=시간, 열=일차)은 `schedule`의 `day`·`start`·`end`·`label`만으로 100% 파생된다.
**새 DB 경로 0개, 새 뷰 1개**만 만든다. 시간 축은 반드시 `scheduleTime.ts`의 헬퍼를 쓴다 — 시트에 `25:00`·`26:00` 행이 실재하므로 24시+ 표기(패턴 11)를 그대로 태워야 한다.

### 4.4b 담당 구역(`detail`)은 구조화한다 — 명찰카드의 열쇠

3.5절 결론 2에 따라 `IguardMovement.detail`을 원문 보존과 파싱값 두 가지로 다룬다.

```ts
/** 담당 구역 파싱 결과. 원문(detailRaw)은 항상 보존하고, 파싱 실패는 null로 둔다. */
export interface AssignedArea {
  building?: string | null;  // "A동" | "C동" | "본관" | "별관"
  floors?: number[];         // [3, 4]  ← "3,4층"
}
```

- `박혜원sf(C동 3,4층)` → `{ building: "C동", floors: [3,4] }`
- `도윤성sf(2층+별관)` → 복수 구역이므로 배열로 보관하고, 파싱 실패 시 **추정하지 않고 원문만 남긴다**(패턴 23의 원칙 — 모호하면 임의 배정 금지).

이 값이 있으면 `rooms`·`students`와 결합해 **"내 담당 구역의 호실별 학생 명단"** 이 자동 생성된다. 이것이 명찰카드의 개인 섹션이다.

### 4.5 자유 메모는 반드시 남긴다

시트 기타 칸에는 제작 중의 생각이 그대로 적혀 있다:

> "방문개방 다시 생각해보자..하.." · "둘날부터 김동연 동선 넣어야함" · "숙소→강당 @이채희"

**정리되지 않은 채로 남아도 되는 칸이 없으면, 제작자는 그걸 적으려고 시트를 열고 그 순간 다시 두 개를 쓰게 된다.** 블록과 구간 모두에 `note` 자유 텍스트를 두고, UI에서 "메모(정리 안 해도 됨)"로 명시한다. 이 칸은 검증 경고 대상이 아니다.

### 4.6 ⭐ 복제 대상 정의 — "구조만 복제"

**전제**: 수련회를 섬기는 사람은 매번 바뀐다. 따라서 복제 모드는 **"구조만 복제" 하나뿐이다.** 사람이 딸려오는 복제 모드는 만들지 않는다 — 이전 담당자 이름이 남아 있으면 새 제작자가 그걸 지우는 일부터 해야 하고, 지우다 남은 이름이 현장 사고가 된다.

핵심은 **동선의 뼈대는 살리고 사람만 비운다**는 것이다. `IguardMovement.staffId = null`(미정 배정, 갭 B)이 이걸 가능하게 한다. 갭 B는 원래 "셋째날 빈칸" 때문에 넣었지만, 실제로는 **복제의 전제**이기도 하다.

| 노드 | 복제 | 무엇을 |
|---|---|---|
| `schedule` (블록) | ✅ | `day`·`start`·`end`·`label`·`detail`·`meal`·`noMovement`. `detail`(분 단위 진행 대본)이 재사용 가치가 가장 크다 |
| `segments` (구간) | ✅ | `label`·`order`·`zone` |
| `posts` (포스트) | ✅ | 전체. 이름은 장소 의존이므로 **복제 직후 일괄 이름 변경**을 거친다 |
| `movements` (동선) | ⚠ **부분** | `segmentId`·`postId`·`round`·`detail` 유지, **`staffId`는 전부 `null`(미정)**, `actor`는 유지(행정팀 등 역할) |
| `seating` (집회 자리) | ⚠ **부분** | 구역 이름·`layoutPattern` 유지, `groupIds` 비움 |
| `meals` (식사 세션) | ⚠ **부분** | `label`·`day`·`slot` 유지, `entries`(조 순서) 비움 |
| `guide` (조스탭 가이드) | ✅ | 전체 (사람 무관 텍스트) |
| 블록·구간의 `note` (자유 메모) | ❌ | 이전 수련회의 미결 메모가 남으면 혼란만 준다 |
| `buses` | ❌ | 장소·인원 의존. 행정 조편성이 오면 자동배정으로 새로 만든다 |
| `gbs` (GBS 장소) | ❌ | 장소·조 모두 바뀌므로 재사용 불가 |
| `groupStaff` (조스탭 배정) | ❌ | 사람 |
| `attendance` (인원체크) | ❌ | 절대 복제하지 않는다 |
| `accessLock` (PIN) | ❌ | 보안 |
| `cueSheet` (시트 설정) | ❌ | 시트 URL이 다르다. P5 이후 이 노드는 역할이 끝난다 |
| `prepMilestones` | ❌ | **전역 공유 노드**(수련회별 아님). 복제 대상이 될 수 없다 |

복제된 레코드는 `source: "cloned"`로 표시해, 제작자가 "아직 손 안 댄 것"을 구분할 수 있게 한다.

## 5. 마이그레이션 ⚠ 사용자 승인 + 스냅샷 백업 필수

### 5.1 원칙

- **무손실**: 기존 동선 214건이 1건도 사라지지 않는다.
- **되돌릴 수 있음**: 스냅샷 하나로 원상복구된다.
- **전체 덮어쓰기 금지**: 루트 CLAUDE.md 실수 #2. 단일 경로 `update()`의 다중 경로 묶음만 사용하고, `set()`으로 `movements` 노드 전체를 쓰지 않는다.

### 5.2 절차

1. **드라이런(읽기 전용)** — 변환 결과를 파일로만 출력한다. 보고 항목: 대상 수련회 수, 기존 동선 건수, 생성될 기본 구간 수, 변환 후 동선 건수, **불일치 0 확인**.
2. **스냅샷** — `retreats/{id}/iguard/movements`와 `schedule`를 JSON으로 내려 `backups/`에 타임스탬프로 저장. 복구 명령을 함께 기록한다.
3. **실행** — 수련회 1개씩. 각 블록마다 **기본 구간**(`order:0`, `label:"전체"`, `source:"manual"`)을 만들고, 기존 동선 `${staffId}__${blockId}` → `${defaultSegmentId}__${postId}__${staffId}`로 옮긴다. `postId`·`round`·`note`·`source`는 그대로 보존.
4. **검증** — 마이그레이션 후 건수 대조 + 개인 큐카드에서 임의 스탭 3명의 동선이 이전과 동일한지 육안 확인.
5. **롤백 기준** — 건수 불일치가 1건이라도 나오면 즉시 스냅샷 복원.

### 5.3 하위호환

- 구버전 키(`staffId__blockId`) 레코드를 읽는 코드를 **한 시즌 유지**한다. `segmentId`가 없는 동선은 해당 블록의 기본 구간에 속한 것으로 간주한다.
- 이 하위호환은 2027 겨울수련회 종료 후 제거한다.

## 6. 단계별 실행 계획

각 단계는 **1단계 = 1커밋 이상**, 기준 검증(`npx tsc --noEmit` 0 errors + `npm test` 전체 통과 + 필요 시 `npm run build`)을 매 단계 통과해야 한다.

### P0. 첫 접촉 난이도 — 복제와 장소 갈아끼우기 (설계 제약)

**문제**: 현재 앱에는 **수련회 복제 기능이 전혀 없다**(2026-07-30 코드 확인). 새 수련회는 포스트 0개·큐싯 0개·동선 0개의 백지에서 시작하고, 제작자는 `PostsView`에서 포스트를 하나씩 손으로 등록해야 한다. 기획 탭 11개 중 어디부터 손대야 하는지 안내도 없다.

반면 시트는 백지에서 시작하지 않는다 — **지난 수련회 시트를 복사해서 고친다**(시트에 "스탭 큐싯 백업본", "2026년 겨울 조장 큐싯" 탭이 남아 있는 것이 그 흔적이다). **시트가 쉬운 이유는 자유 입력이 아니라 0에서 시작하지 않는다는 것이다.**

따라서 P1~P6이 개념(구간·미정 배정·actor)을 늘리는 만큼, 복제가 없으면 **앱은 지금보다 어려워진다.**

**P0는 독립 단계가 아니라 전 단계에 걸리는 제약이다:**

1. **P1의 모델 설계는 "복제 가능해야 한다"를 전제로 한다.** 모든 id는 push id이고, 참조는 id로만 이뤄져야 복제 시 재매핑이 기계적으로 가능하다. 4.2절의 동선 키 `segmentId__postId__staffId`는 이 조건을 만족한다.
2. **복제 UI는 P5(에디터)와 함께 낸다.** 복제해도 앱에서 고칠 수 없으면 반쪽이기 때문이다.
3. **포스트 일괄 이름 변경 화면**을 함께 만든다. 매 수련회 바뀌는 것은 구조가 아니라 **어휘**다 — `시간 블록 → 구간 → 포스트 → 사람`이라는 뼈대는 그대로이고 "강당·별관 201호·A동 3층" 같은 이름만 바뀐다. 포스트가 참조 관계이므로 **이름만 바꾸면 동선 배정이 그대로 살아 있다.** 시트에서는 여러 탭에 찾아바꾸기를 돌려야 하는 작업이라, **여기서는 앱이 시트보다 확실히 쉽다.**

**앱이 시트보다 쉬운 지점도 정직하게 센다** (제작자 설득 논거):
- 시트의 표기 관행(`sf` 꼬리표·`[선밥]`·`* 구간`·`- 포스트: 이름`)은 전부 암묵지다. 새 제작자가 눈치로 배우고 빠뜨리면 임포트가 조용히 실패한다(`busStaff.ts`가 "스탭 0명" 같은 오염을 걸러내는 코드가 그 증상이다). 앱에서는 이것이 **입력칸과 선택지**가 되어 표기법 사고가 사라진다.
- 스탭 명단·조편성·버스는 행정에서 자동으로 넘어온다. 시트에 손으로 옮겨적는 일 자체가 없다.

**정직하게 남는 한계**: 예상 못 한 것을 아무 칸에나 적는 자유도는 구조적으로 못 따라간다. 완화책은 4.5절 자유 메모뿐이고, 그것으로 다 덮이지 않는다.

### PA. 지금 바로 할 수 있는 것 (모델 변경 불필요, 선착수 가능)

아래 3개는 P1~P6과 독립이며 **오늘 코드 기준으로 바로 구현 가능**하다. 효과 대비 비용이 가장 낮으므로 먼저 낸다.

- 동시 편집 안전성: 단일 경로 `update()`만 사용. 인원체크와 동일한 원칙(패턴 15) — `set`으로 목록 전체를 쓰지 않는다.
- 시트 임포트는 **초기 1회 마이그레이션 도구**로 격하한다(상시 동기화 아님). 격하 시점에 패턴 19의 신선도 배너는 역할이 끝난다.
- **P0의 복제 UI와 포스트 일괄 이름 변경을 함께 낸다** (4.6절 복제 대상 표 그대로).
- ⚠ **완료 조건 = 9장 관찰 테스트 통과.** 기능이 다 있어도 테스트를 통과하지 못하면 P5는 완료가 아니다.

### P6. 현장 딜레이 대응 (축 4)
- 블록에 `actualStart` 개념 추가 → "지금 여기까지 왔음"을 찍으면 이후 일정이 함께 밀린다
- 개인 큐카드의 고정 카드는 계획 시각이 아니라 **진행 상태** 기준으로 판정
- 피드백 D의 "전·후 일정을 보려는데 현재 일정이 고정돼 있어 어려웠다"를 여기서 해소
- ⚠ 시계 tick으로 사용자 선택을 덮지 않는다(패턴 17)

**P6 이후에도 남는 것**: 갭 C의 "조스탭 불가" 표기. 행정 `teachers`에 필드 추가가 필요해 **행정 앱과 협의 대상**이다. 이가드 단독으로 결정하지 않는다.

## 8. 행정 앱과 협의해야 하는 것 (이가드 단독 결정 불가)

### 8.1 ⚠ 현장 정보 변동 반영 — **범위 밖이 아니라 필수다**

이전 판에서 "범위 밖"으로 뺐으나 근거가 3건으로 늘어 되돌린다.

> 최성우: *"정보가 어떻게 잘 업데이트되게 할 수 있을까 (**후발, 선복귀** 등)"*
> 김수현: *"**후발, 선복귀 체크하기가 사이트 상에서 좀 어려웠던** 것 같아"*
> 김성훈: *"**이가드 사이트를 했던 이유는 행정에서의 정보변동의 유실**이었지"*

마지막 인용이 결정적이다 — **이것이 이 사이트의 원래 존재 이유다.** 자차 전환·후발·선복귀가 현장에서 반영되지 않으면 명단과 현실이 어긋나고(피드백 C의 "2호차 명단에 있는데 실제로는 자차 이동"), 그러면 앱 전체의 신뢰가 무너진다.

협의할 것: 현장 변동을 **누가 어느 노드에 쓰는가**. 후보 (a) 행정 앱이 계속 소유하고 이가드는 요청만 보낸다, (b) 이가드가 쓸 수 있는 별도 오버레이 노드를 둔다. **어느 쪽이든 `DB_OWNERSHIP.md` 갱신이 선행되어야 하며, 합의 전에는 코드를 쓰지 않는다.**

### 8.2 학생 속성 (수찬·선교팀 등)

명찰카드에 `18:40 수찬 학생들`, `선교 학생` 명단이 있다(3.5절). 이런 임의 분류가 행정 데이터에 있는지 확인되지 않았다. 없다면 행정 `participants`에 태그 개념을 추가할지 협의한다.

### 8.3 "조스탭 불가" 표기 (갭 C)

시트에서 밑줄로 표현되는 값. 행정 `teachers`에 필드 추가가 필요하다.

## 8b. 범위 밖 (이번에 하지 않는 것)

- **축 6 동선 약도·사진** — 근거 1건이며, P3에서 동선 구조가 바뀌므로 지금 만들면 두 번 만든다. P4 이후 재검토
- **프로그램 시트 연동** — 설문 ⑦ 제안. 본인도 "무조건 추가되어야 한다는 건 아님"이라 명시. 큐싯 저작이 자리잡은 뒤 재검토
- 조장 큐싯·집회 자리·버스·할일 탭 — 앱에 이미 있으므로 이번 리모델링 대상 아님

### 축소도 함께 한다 — 현장/준비 모드 분리

> 최성우: *"진짜 필요한 거는 **인원 체크랑 숙소, 조별 정보, 개인 동선**. 그 외에 필요한가"*
> 설문 ⑦: *"식사순서와 자리배치는 수련회 전에는 유용했으나 현장에서는 사용할 일이 없었음"*, *"조스탭 가이드 → 이 친구들이 이거 한번이라도 보긴 했을까? 없어도 무방함"*
> 김수현: *"집회자리 탭이 무쟈게 폭력적이었다"*

이 설계서는 기능을 **추가**하는 방향(구간·GBS·개요 격자)이다. 그대로 두면 첫 접촉 난이도가 다시 올라간다. 따라서 같은 분량의 **축소**를 함께 한다:

- 현장(모바일) 기본 노출은 **인원체크·숙소·조별정보·개인 큐카드 4개**로 좁힌다
- 식사순서·집회자리·조스탭 가이드는 **준비 전용**으로 명확히 분리한다(삭제 아님 — 준비기간에는 유용하다고 ⑦이 명시)
- 삭제 여부는 9장 관찰 테스트 결과로 판단한다

## 9. 난이도 검증 — 관찰 테스트 (P5 완료 조건)

**난이도를 우리가 판정하지 않는다.** 설문 6건으로는 "처음 쓰는 사람이 막히는 지점"이 절대 나오지 않는다.

**절차**
1. 큐싯을 만들어본 적 없는 스탭 **1명**을 섭외한다.
2. **아무 설명 없이** "다음 수련회 큐싯 초안을 만들어보세요"라고만 말한다. 옆에서 돕지 않는다.
3. 30분 동안 관찰하며 기록한다:
   - 막혀서 멈춘 지점과 그때 화면
   - 질문한 횟수와 질문 내용
   - **"시트를 열고 싶다"고 말하거나 실제로 연 순간** ← 가장 중요한 신호
   - 완성한 블록 수
4. 통과 기준: **설명 없이 시간 블록 3개 이상을 구간·포스트까지 채운다.** 미달이면 P5는 완료가 아니며, 관찰 기록을 근거로 UI를 고치고 다른 사람으로 재테스트한다.

**지금 당장 할 수 있는 사전 관찰**: P5를 기다리지 않고, 다음 큐싯 제작자가 정해지는 즉시 **현재 앱**으로 같은 관찰을 한 번 한다. 설계 방향이 바뀔 수 있는 정보이므로 빠를수록 좋다.

## 9b. 도입 전략 — 기능이 아니라 운영 결정 ⚠

행정 앱이 성공한 원인은 UI가 아니었다.

> 김수현: *"행정은 이번에 **시트도 안 만들고 아예 사이트로만** 했기 때문에 안 익숙해도 어쩔 수 없이 많이 쓰고 익숙해질 수 있었는데, 이가드는 만들어진 지 얼마 안 됐고 잘 쓸 줄도 몰랐어서 급하니까 시트를 이용했단 말이지. (…) **애초에 기획부터 사이트에서 할 수 있게끔 해야** 많이 쓰게 되지 않을까"*

**퇴로를 없앤 것이 성공 요인이었다.** 따라서 이행 시점을 미리 정한다:

1. **P5 완료 + 9장 관찰 테스트 통과** 후 첫 수련회부터, **큐싯 스프레드시트를 만들지 않는다.**
2. 그 전제로 **P0b(명찰카드 인쇄)가 먼저 동작해야 한다.** 종이가 앱에서 나오지 않으면 퇴로를 끊을 수 없다.
3. 이행 수련회에는 **롤백 조건을 미리 정한다** — 리허설 QA에서 치명 결함이 나오면 시트를 병행한다. 현장에서 즉흥 판단하지 않는다.

### 조직 전제 (코드로 해결 불가)

> 최성우: *"행정은 우리가 쓰는데 우리가 만들었고 피드백이 계속돼서 수정을 많이 했는데, **이가드는 만들어서 그냥 투척한 느낌**이라서"*

행정은 **만든 사람 = 쓰는 사람**이라 피드백 루프가 짧았다. 이가드는 그 루프가 없다. 다음이 전제되지 않으면 이 설계서의 어느 단계도 실효를 갖기 어렵다:

- 이가드 안에 **큐싯 제작 담당자를 지정**하고, 개발이 그 사람과 직접 붙는다
- 9장 관찰 테스트를 그 사람으로 진행한다
- 준비 기간 중 최소 1회 이상 피드백 → 수정 사이클을 돈다
